# 漏洞验证与反例检查

## 确认门槛

最小化指减少副作用，不是省略必要证据。一个发现只有同时满足以下条件才可标为已确认：

1. 目标和实验动作获准，身份及资源归属可追溯。
2. 存在有来源的安全/业务规则；记录预期行为与正常基线。
3. 实际实验突破该规则，结果可从原始证据复核，不仅是 HTTP 或工具成功。
4. 已排除与本次判断相关的替代解释：合法共享、会话混用、登录页、缓存、异步未完成、网络抖动等。
5. 影响描述不超过证据能力；每个结论引用具体实验和证据。

可在无额外明显副作用且预算允许时复测。一次性或有状态问题不为追求重复次数而重放危险动作；保留操作记录和前后状态，并说明复现限制。不能稳定复现不自动等同 Ignore。

## 技术确认之后仍需判断影响

上述门槛只确认假设描述的安全/业务边界被突破。不能把原漏洞假设改写成普通观察现象后标 confirmed；观察事实与漏洞假设状态分开记录。按 [企业影响与收录](impact-and-acceptance.md) 独立给出 impact_status 和 submission_assessment：原型属性改变、模板计算、WAF 放行等即便某种能力成立，也不能直接作为可提交漏洞。确认真实业务影响或达到当前规则明确认可的有限能力证明，且无已知排除项，才进入待提交队列。

确认可以使用自建身份/资源代表权限边界，不要求侵害真实用户；平台认可的 SSRF 回显、隔离证据或其他最低证明条件满足后停止，不为规模和等级继续扩大影响。证实无有意义影响与尚缺证据要区分，平台不收录也不能反向抹去技术事实。

## 观察与结论

| 观察 | 当前能支持什么 | 还缺什么 |
|---|---|---|
| 扫描命中、版本匹配、错误堆栈 | 检测线索 | 适用配置、可达入口与最小真实验证 |
| HTTP 200 / 有响应 | 请求获得响应 | 应用语义、身份、受保护数据或实际状态变化 |
| 两个响应长度不同 | 有差异 | 具体字段、对照实验及差异因果 |
| DNS 回连 | 某组件解析了唯一标记 | 触发归因、是否违反边界；不推出 HTTP 读取或 RCE |
| 单次延迟 | 时延异常 | 基线分布、交错对照、负载/限流排除 |
| 上传成功 | 文件被接收 | 存储、处理、权限或执行边界是否被突破 |
| 已授权身份取得自己资源 | 正常基线 | 不具备权限的测试身份对同一规则的验证 |

## 分析步骤

先写观察事实，再解释，不从漏洞名称倒推事实。对写操作核对权威状态；对异步动作记录任务 ID 和完成条件；对身份测试使用独立会话及身份核对证据。

规范化比较只忽略已明确的动态噪声字段，并保存忽略清单；不要过滤权限字段、错误码、资源归属或关键内容。需要截图时补充截图，但截图不能替代请求和状态证据。

## 分级记录

线索 → 待补证 → 已确认并不是自动流水线，结果也可以是本次未复现或受阻。工具执行失败必须单独记录。详见 [状态](state-and-evidence.md)。模型置信度和第二次模型同意均不能替代以上确认门槛。

对报告做一次反例复核：如果这是预期行为，最可能的解释是什么，现有证据是否排除了它。无法排除时保留不确定性，避免提高测试影响来强行确认。
