# 贝壳 BKSRC 规则配置

仅当项目实际采用贝壳 BKSRC（贝壳安全应急响应中心）规则时读取。核对来源（查阅于 2026-09-24）：主规范 [《安全漏洞及威胁情报处理规范 V3.1》](https://security.ke.com/notices/details?id=54)，2026-08-18 生效；[《关于 BKSRC 进一步规范漏洞报告提交的公告》](https://security.ke.com/notices/details?id=55)，2026-08-24 生效；[《关于 AI 辅助漏洞报告提交规范的公告》](https://security.ke.com/notices/details?id=53)，2026-07-15 生效；[《白帽测试规范及违规处理规定 V2.3》](https://security.ke.com/notices/details?id=50)，2025-11-27 发布；[《BKSRC 现金兑换说明 v4.0》](https://security.ke.com/notices/details?id=52)，2026-04-07 发布。

已读取各公告网页文字与 V3.1 内嵌图片（反馈流程图、积分标准表经 OCR 与公式交叉验证）。本文件为决策摘要，不是完整规则或永久有效的授权：先记录 project、policy_version（V3.1 与公告 id）、checked_at、适用条款与证据引用，规则登记到现有运行说明，不新增宿主 API 字段；规则不清只阻塞相关定级、收录或奖励判断，不抹去技术事实。原站为前端渲染页面，直接抓取为空；核对原文可用 POST https://security.ke.com/api/notices/details（JSON body：{"id":"<公告 id>"}），内嵌图片经 POST /api/img/public?hash=… 获取。

## 适用范围与计分资产

- 适用于 security.ke.com 收到的贝壳所有产品及服务安全漏洞报告；平台同时受理威胁情报。提交渠道：平台账号或 bksrc@ke.com。
- 计分域（原文"包括但不限于"）：*.ke.com、*.lianjia.com、*.realsee.com、*.ehomepay.com.cn、*.bkjk.com。
- 非贝壳直接发布的产品和服务暂不计分（如自如、各城市私建系统）；归属存疑先核对归属，不把第三方系统计入。
- 核心应用及业务：贝壳找房官网、链家官网、贝壳找房 APP、链家 APP、Link APP、通用核心功能（如统一登录）等。
- 定级以对业务的实际影响为准；同一漏洞在不同业务场景可有不同等级。

## 测试行为红线（测试规范 V2.3，已有公开处罚先例）

1. 注入：只证明可以读取；严禁读取表内数据；UPDATE、DELETE、INSERT 类注入不允许使用自动化工具。
2. 越权：读取真实数据不超过 10 组，严禁批量读取（V3.1 亦要求验证数据不超过 10 条）。
3. 账号：只允许用自己的 2 个账号验证，不涉及线上正常用户账号；越权增删改只用自有测试账号。
4. 禁止借用或获取内部账号（链家经纪人、贝壳内部员工、加盟服务商等）；禁止社工、钓鱼获取产品信息或内部账号；通过漏洞获得内部权限应优先提交权限提升漏洞。
5. 存储 XSS：插入不影响他人的测试 payload，严禁弹窗（推荐 console.log），用另一个自有账号验证并提供截图；盲打类仅允许外带 domain 信息；测试后删除插入数据，不能删除时在报告备注插入点。
6. RCE/命令执行：推荐仅上传证明文本（如含回显 print 功能）；禁止下载、读取服务器任何源代码和敏感文件；不执行删除、写入命令。
7. 扫号类（短信/邮件未限次）：测试成功数量不超过 50；用户可感知（如登录提醒短信）时不允许对他人真实手机号测试。
8. 自动传播/扩散类（如社交蠕虫）：只允许使用与他人隔离的小号。
9. 禁止使用漏洞扫描器探测贝壳产品与服务。
10. 未经特别获准，禁止与漏洞无关的社工与内网渗透。
11. 禁止可能引起业务异常的测试（含 DoS/DDoS 类，如 IIS 拒绝服务测试）。
12. 超范围资产先经 security@ke.com 确认归属后再挖掘；未授权风险自担。
13. 禁止拖库、随意大量增删改他人信息、影响服务稳定性的扫描及黑灰产行为。
14. 禁止保存和传播业务相关敏感数据（含服务器与 GitHub 等渠道泄露的源码、运营数据、用户资料）；不知情下载须及时说明并删除。
15. 禁止谎报、伪造、隐瞒漏洞来源，或干扰审核谋利。
16. 禁止共用测试账号、共享漏洞信息等违反保密规定的行为。
17. 遵循《网络安全法》；禁止以测试为借口破坏、损害用户利益；禁止威胁恐吓 SRC 或擅自向第三方披露（含社交平台），对外披露须先获授权。

处罚对照（V2.3 §二）：违规初犯 = 漏洞降级 + 全站通报；二次及以上 = 取消年度/季度/月度评奖资格并取消该漏洞奖励；三次及以上或情节严重 = 终止合作。读取真实数据超过 500 条须接受违规处理、签署保密协议并协助删除。未获同意公开漏洞内容（不论是否已提交）取消奖励并保留追责；因违规被封的账号不协助找回、积分不补发。平台对违规处罚有公开执行先例（2025-09 违规测试处理公告）。

## 提交、审核与报告格式（V3.1 §三 + 公告 id=55）

- 提交：平台提交或邮件 bksrc@ke.com（主题注明"BKSRC--漏洞/威胁情报提交"；含名称、位置及潜在危害、复现步骤、脚本等材料与修复方案，敏感信息建议加密）。
- 时效：7 个工作日内确认收到并跟进评估；14 个工作日内完成确认、评级与奖励评测；忽略与重复会说明原因。
- 修复与确认：确认后由业务修复上线（时长依严重程度与修复难度）；复测验证成功后提交者确认；确认的报告获得积分，可兑换礼品。
- 报告格式（id=55 强制）：标题 〖漏洞类型〗+〖影响资产/域名〗+〖漏洞简要描述〗；正文五模块——①详细说明（结合业务实际影响，避免笼统）；②测试账号、IP 地址及测试时间；③漏洞证明（完整可复现步骤 + 截图，应可 100% 复现：发现链路、验证利用流程、成功结果证明、所用全部工具、原始请求/响应数据包）；④切实可行的修复方案；⑤联系方式（平台未实名，用于确认与奖励发放）。
- 不规范报告（缺信息、排版混乱、无法稳定复现、只给请求不解释步骤等）直接驳回且不另行说明；无法证明的危害不得在标题或描述中夸大。

## AI 辅助报告要求（公告 id=53、id=55 §三）——直接约束本 skill 的交付

- 允许并鼓励 AI 辅助/自动化挖掘，但提交前必须人工验证；报告真实性责任由提交者承担。
- 四项必备材料（缺一不可）：①结合业务场景的危害性说明；②可重复的复现步骤（独立于 AI 输出，以亲自实测流程为准）；③完整可运行的 POC（脚本、命令或 HTTP 报文，标注关键参数）；④关键环节截图（关键交互节点与最终成功触发界面/日志）。
- 直接不予受理或驳回的情形：报告全部或明显由 AI 生成且无人工验证痕迹；缺失任一必备材料；复现步骤与实际不符或 POC 无法执行且与 AI 原始输出高度相似。
- 账号级后果：累计 3 个未经有效人工验证的 AI 报告 → 书面提醒；累计 5 个 → 暂停或终止提交权限（拉黑）并取消已获活动奖励资格；恶意批量制造虚假漏洞 → 永久封禁并保留法律追责（不设阈值）。
- 交付含义：候选报告必须自带可复现证据与人工可复核材料；不得把未经复现的模型输出当作报告提交；材料不齐按 needs_evidence、missing_requirements 记录，不冒充已满足。

## 漏洞评级参考（V3.1 §四.3，实际定级以 BKSRC 审核为准）

| 等级 | 参考条件要点 |
|---|---|
| 严重 | 核心系统权限（RCE、任意代码执行、任意文件上传获取 shell、核心 DB 注入）；公司机密级信息（如未授权接口访问）；核心业务用户信息丢失或资金损失（统一登录任意账号登录/改密、任意账号资金消费、支付交易逻辑）；核心业务拒绝服务 |
| 高危 | 一般系统权限（非核心 RCE、可 dump 数据注入等）；商业秘密级信息（重要敏感数据泄露）；重要未授权访问（绕过认证访问含敏感信息管理后台、核心业务敏感信息未授权、核心后台弱口令且具实际操作权限、越权查看任意用户敏感信息、可获取大量内网敏感信息的 SSRF）；重要活动逻辑（刷红包、刷金币等直接较高利益或大量损失）；核心系统重要交互页面存储型 XSS（可获取 cookie 等或具传播性）；统一登录体系暴力破解 |
| 中危 | 需交互才能影响用户（一般页面存储 XSS、敏感操作 CSRF）；普通信息泄露；普通未授权操作（破坏性越权编辑/删除/查看非核心系统信息）；普通逻辑/流程缺陷（非核心业务规则绕过） |
| 低危 | 特定情况才能获取用户信息（反射 XSS、边缘业务存储 XSS）；轻微信息泄露；URL 跳转等轻微影响；利用成本很高的隐患（特殊条件 MITM、需用户连续交互） |
| 无影响（忽略） | 非安全 Bug（功能缺陷、乱码、样式、静态目录遍历、兼容性）；不可利用项（Self-XSS、PDF XSS、无敏感操作 CSRF、无敏感信息 JSON Hijacking、无意义源码泄露、无实际影响的批量操作、内网 IP/域名/路径泄露、401 基础认证钓鱼、程序路径信任、横向短信轰炸、无意义扫描器报告如 Web Server 低版本）；无法重现；内部已知/处理中（含 Discuz! 等公开通用、白帽或内部已发现）；上传超一年的网盘泄露；无危害枚举（用户名、手机号注册枚举）；业务需求导致的可接受设计缺陷 |

## 威胁情报评级参考（V3.1 §四.4，实际定级以 BKSRC 审核为准）

| 等级 | 参考条件要点 |
|---|---|
| 严重 | 核心业务系统完整入侵证据/线索（如核心生产服务器被传 webshell）；重要业务数据库被拖取并提供数据库名/文件线索（用户个人信息、交易信息等）；对核心产品服务有重大直接影响的黑灰产详细情报 |
| 高危 | 非核心系统完整入侵证据/线索（帮助溯源、定位攻击者）；对核心产品服务有较大影响的黑灰产详细情报 |
| 中危 | 对特定产品服务有一定影响的黑灰产详细情报；可帮助完善防御体系（防高风险及以上新型攻击）的详细情报 |
| 低危 | 少量作弊线索、黑灰产组织结构信息；社会舆情（涉贝壳恶意言论等） |

## 积分与奖励（V3.1 §四.2/§五 + 兑换说明 v4.0）

- 公式：奖励积分 = 漏洞等级数值 × 等级系数 × 业务等级数值；系数会按实际情况调整（调整以公告为准）。
- 积分参考区间（官方积分表，经公式交叉验证）：

| 类别 | 严重（9-10） | 高危（6-8） | 中危（3-5） | 低危（1-2） | 无危害（0） |
|---|---|---|---|---|---|
| 等级系数 | 8 | 4 | 2 | 1 | 0 |
| 核心业务（12-16） | 864–1280 | 288–512 | 72–160 | 12–32 | 0 |
| 一般业务（3-8） | 216–640 | 72–256 | 18–80 | 3–16 | 0 |
| 边缘业务（2） | 144–160 | 48–64 | 12–20 | 2–4 | 0 |

文字版 5 档为"严重/高危/中危/低危/无影响（忽略）"；表中"无危害"即最低档（0 积分）。

- 日常奖励：积分兑换礼品；每月月末发放上一轮兑换；资料不全导致延误顺延；因报告者过失或不可抗力造成的丢失/损坏不担责。其他奖励（积分排行榜、优质漏洞、节假日福利等）以活动公告为准。
- 现金兑换（v4.0）：每月 10 日前统计、15 日结算发放（特殊情况可能后移）；自 2026 年起按劳务报酬预扣税金并由平台代申报代缴；需本人真实信息并签署三方承揽协议（首次兑换后 1 个工作日内）；存在禁止合作人群（外籍、与公司有劳动/劳务关系、<18 或 >65 岁、军人/公职人员等禁止兼职者、个体户经营者/法定代表人等），资格细节以原文为准。

## 重复、同源与降级（V3.1 §四.5 + V2.3 §二）

- 重复：同一漏洞首位报告者计分，其余忽略。
- 同源合并：同一漏洞源产生的多个漏洞计为一个（链家与贝壳同一功能、同一 JS、服务器/应用框架、泛域名解析等）；全站未鉴权或房江湖账号登录后同站点多个接口未授权/越权合并为一个并提高分数；分散提交只收第一个；恶意拆分由平台降级处理。
- 降级情形：无法稳定复现或步骤不完整；影响范围小（历史系统、少量数据、用户有限、未正式投用）；利用条件苛刻（特殊账号权限、id 复杂等）；利用场景复杂（极小概率且难造成实质危害）；业务预期内资损/风险可控 → 降级或忽略。
- 与贝壳无关的漏洞或威胁情报不计分。

## 争议与交付

- 异议：通过报告页面评论功能反馈；BKSRC 按报告者利益优先原则处理；规范最终解释权归 BKSRC。
- 交付候选附：rule_ref（V3.1 条款 + id=55/id=53 报告要求）、checked_at、已证明前提、忽略项检查、最小化数据说明（≤10 条）、附件与人工验证缺口、奖励依据。
- 等级、积分与受理均为候选判断（"实际定级以最终审核结果为准"），可提交不等于已接收或获奖；平台重复库不可见时保留未知。
- 平台侧约束不改变 [执行边界](../../SKILL.md)；本文件不能让未授权动作合法化。
