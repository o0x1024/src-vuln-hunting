## 适用与版本判据

- 平台受理范围是"通过 security.jd.com 反馈平台收到的所有威胁报告"，含 web/客户端漏洞、威胁情报、通用组件与插件漏洞（V8.0 §1、§3.1）。
- 资产边界示例（V8.0，原文为"等"，不能当穷举白名单）：京东商城 `*.jd.com`、`*.jd.hk`；1 号店 `*.yhd.com`、`*.yihaodian.com`、`*.1mall.com`；京东物流 `*.jdwl.com`、`*.jclps.com`；京东海外 `*.joybuy.com`、`*.jd.ru`、`*.jd.co.th`、`*.jd.id`；京东医药 `*.healthjd.com`、`*.yiyaojd.com`；7FRESH `*.7fresh.com`；京东金融 `*.jr.jd.com`、`*.baitiao.com`、`*.jdpay.com`、`*.wangyin.com` 等；京东云 `*.jcloud.com`、`*.jdcloud.com`；京东安联 `*.jdallianz.com`、`*.allianz.cn`；京东云配 `*.yunpei.com`、`*.yunxiu.com`。域名在列不等于当前授权，也不等于本次可测动作获准。
- 版本关系：公告 287（V9.1，2025-07-31）最新；公告 255 的 V8.0 全文（2022）用于未被 V9.1 覆盖的细则（流程、评分表、通用原则）。两者冲突时以最新公告为准，并把无法对齐的点记为 rule_review。

## SSRF 收录标准（公告 287 OCR 表 + V8.0 通用原则 23）

- 测试必须使用京东安全官方提供的目标：`http://ssrf.jd.local/c3f3f53c12674acdc9855f47b85299f0.html`；未使用该目标视为无效且不予计分（V8.0 原则 23、公告 274 §3、公告 287 §04/§05）。
- OCR 表结构（列：资产类型 / 危害 1 回显程度 / 危害 2 可利用协议 / 漏洞等级）。OCR 读到的单元格：全回显 + gopher 协议 = 核心严重；另有 核心高危（1000 分）一档；无回显或不完全回显但可向内网主机发送任意 payload（http/file 协议）= 核心中危（120 分）；无回显或不完全回显且只能用固定格式探测标准、无法发送任意 payload（http/file 协议）= 核心中危（60 分）；一般资产（京东云内网、京东金融内网、京东五星内网、京东保险内网等）= 一般中危至一般严重；边缘资产（VPC 隔离区但有其他资产）= 边缘中危至边缘严重；不收取的资产（VPC 隔离区内网且没有其他资产、不通内网）= 忽略。
- OCR 行与列的配对未能完全确认（1000 分档与 120/60 分档的对应关系需回原图核对），引用具体分值前先核对原图；不得用其他平台"回显 SSRF 即高危"的口径套用京东，也不得把本表当成所有项目通用。
- OCR 存在识别误差（如"通核心 IDC 内网"），具体档位回原站核对；不得用其他平台"回显 SSRF 即高危"的结论套用京东，也不得把本表当成所有项目通用。
- 表格与"仅证明 DNS 查询/外带 domain 信息"一类现象不能混用：无回显档位仍要求能向内网发送任意 payload 或使用固定探测格式，纯 DNS 事件不自动满足。

## 降级场景（公告 287，V9.1）

各等级漏洞的最终积分由利用难度及影响范围等综合因素决定，经审核可能跨等级调整积分。公告列出的降级情形：

- SQL 注入若无敏感数据、或敏感数据不满足数据泄露高危标准则降级。
- RCE 位于云 VPC 且容器因功能需求动态生成时降级或不做处理。
- 需要受害者交互的场景，如发送链接点击、查看消息或邮件等。
- 影响范围极小、只有少量注册用户的新/旧系统。
- 未经授权使用非本人账号在系统内进行安全测试（也禁止用非本人账号做功能操作，如添加权限）。
- 触发条件非常苛刻（如特定浏览器才可触发的 XSS）、特殊时期（如双 11 活动内传播影响大的业务逻辑漏洞）、需要特殊账号权限才能发现利用的漏洞。
- V8.0 补充口径：非京东商城发布的产品/业务（投资公司、子公司、合资公司等）降分或降级，等级不超过中危；京东云合作业务（如 cpsc.jcloud.com）按业务影响降分；云市场、教育云、产业云、城市云、县域之窗等第三方/SaaS 业务降分或降级且不超过边缘中危；京东云租户业务不积分（义务通知租户）。

降级是积分/定级结论，不是技术结论；技术事实、证据与清理状态仍按 [验证标准](../verification.md) 保留。

## 不收录与忽略

公告 287（V9.1）列出的忽略类型：违规测试；邮箱轰炸；横向短信轰炸；短链接爆破；非信息安全问题；子账号越权主账户；ISV 业务低危漏洞；`jcloud-oss` 域名下的上传漏洞；内容安全问题与隐私合规问题；网络拒绝服务（DoS/DDoS）；`jcloudcs.com` 域名下的文件上传漏洞；边缘资产低危漏洞（如云鼎）。

V8.0 §3.2 忽略清单（与上表并用）：无法利用/无实际危害（不可利用 Self-XSS、非重要交互 CSRF、静态文件目录遍历、401 认证钓鱼、内网 IP/域名、无敏感信息 JSON Hijacking、横向短信轰炸等）；不能重现；内部已知/正在处理；内部已有审核机制的提交接口自身的 CSRF、越权提交；非接收范围；无安全影响的 Bug（功能缺陷、乱码、样式）；无实际意义的扫描器结果报告；无证据支持（如"账号被盗即代表有漏洞"）；对任意指定用户/手机号无限制的短信轰炸小于 50 条/单手机号/分；需要发送大量请求的拒绝服务漏洞。

判定顺序：先按 [业务预期与权限判定](../business-intent.md) 确认是否越界，再按本节与 [影响与收录](../impact-and-acceptance.md) 判断收录。公开/匿名可访问能力、扫描器命中、无差异响应都不自动成为可提交成果。

## 测试红线与合规（公告 274 测试规范 + 公告 287 §05 + V8.0 通用原则）

1. 禁止使用扫描器或其他自动化工具，仅允许手工测试；影响业务运行将封号处理。本 skill 的 fuzzing/批处理分支在京东项目下必须单独获得明确授权并匹配该条，否则不执行。
2. 测试账号必须说明来源，否则视为盗用账号；禁止使用非本人账号做功能操作（V8.0 原则 11、V9.1 降级场景）。
3. SSRF 必须用官方目标测试（见上节）；命令执行类漏洞须先联系 JSRC 运营报备，经授权后才可继续测试；SQL 注入必须手工注入。
4. 数据量（原文存在版本差异，取更保守值并记 rule_review）：公告 274 §4 注入"获取的数据量不超过 5 条"、公告 287 §05 只允许读取数据库名并禁止读取表内容；V8.0 原则 25 为 ≤50 条、原则 14 为获取十条以上追责。越权读取真实数据不超过 5 组、严禁批量（274 §5）。
5. 存储型 XSS：插入不影响他人的测试 payload，严禁弹窗（推荐 console.log），用另一个自己的账号验证并提供截图；盲打类仅允许外带 domain 信息；测试后删除插入数据，不能删除时在报告中备注插入点（274 §7）。
6. 命令执行/Shell：推荐上传纯文本证明文件（如 1.php、1.jsp）即可，禁止下载读取服务器源代码与敏感文件，不执行删除/写入命令；上传 webshell 需写明地址与连接口令（274 §8、V8.0 原则 15）。
7. 扫号类（短信/邮件未限次）：测试成功数量不超过 50；用户可感知（如登录提醒短信）时不允许对他人真实手机号测试（274 §9、V8.0 忽略项 9）。
8. 自动传播/扩散类（如社交蠕虫）：只允许使用与他人隔离的小号（274 §10）。
9. 未特别获准：禁止与漏洞无关的社工，禁止内网渗透；禁止邮件钓鱼/社工攻击内部员工。
10. 禁止可能引起业务异常运行的测试，包括 IIS 拒绝服务等 DoS/DDoS（含 Syn Flood、CC、各类反射）。
11. 不要对未授权厂商、未分配的项目、超出测试范围的列表挖洞，先联系管理员确认归属（274 §13）。
12. 禁止拖库、随意大量增删改他人信息、影响服务稳定性的扫描，禁止把漏洞用于黑灰产（274 §14）。
13. 禁止保存和传播业务相关敏感数据（含服务器与 GitHub 等渠道泄露的源码、运营数据、用户资料）；不知情下载须及时说明并删除（274 §15）。威胁报告禁止存放在互联网开放云服务（云盘/云笔记等），否则当前报告不计分（V8.0 原则 1）。
14. 线上增删改只用自有测试数据，数据标题或明显字段加"【我是测试】"字样，避免操作正常用户数据（V8.0 原则 10）。
15. 遵守《网络安全法》；禁止以测试为借口破坏或损害用户利益，禁止威胁/恐吓 SRC 公开漏洞或数据，禁止擅自向第三方披露，未修复前主动公开的报告不计分（274 §16、V8.0 原则 2/13/18）。
16. 违规处罚：影响小警告；影响较大视业务资损与数据量扣奖励并保留法律追责；影响严重取消活动参与与特殊奖励；触犯《网络安全法》相关条款将取消全部 SRC 奖励（274 处罚条款）。

本项目内默认执行本 skill [执行边界](../../SKILL.md) 与 [授权与预算](../scope-and-rules.md) 的保守上限；两者与 JSRC 规范同时生效，取更严格者。

## 提交、处理与报告（V8.0 §2/§3.5）

- 流程：提交（域名、潜在危害、复现步骤、修复建议）→ 1 个工作日内确认评估，非工作日严重/高危 24 小时内值班确认 → 确认后 3 个工作日内处理计分 → 必要时挂起（7 天内未补充细节则超时忽略，可重新提交）→ 修复（严重 24 小时、高危 3 天、中危 7 个工作日、低危 14 个工作日；客户端与特殊业务可能变化）→ 已修复后可复查，确认问题仍在可再提交；已确认漏洞 3 个月后仍存在可再提交。
- 报告五要素（首提必须齐全才是加分必要条件）：标题、摘要、复现方法、利用证明、修复方案。标题含影响域名、参数与漏洞类型；摘要含归属、漏洞类型、漏洞危害；复现方法含账号来源、测试账号、出现点与请求方式、数据包/payload/代码、操作思路与工具、环境依赖，复杂漏洞建议视频/截图/PoC。
- 证据硬要求：越权需要两个账号测试，仅凭返回包响应码不能作为利用成功依据（V8.0 原则 21）；提交需提供明确依据。
- 通用原则：同一漏洞多个利用点按最高级别执行；同一系统只收取前三个接口产生的同类型漏洞，时限 3 个月（如同一 JS 的多个 XSS、同接口多参数、同一发布系统多页面、通用框架整站问题合并处理）；同一问题最早提交者得分，网上已公开的报告不计分；不同系统漏洞建议分开提交；非京东商城发布的业务降分或降级。
- 奖励口径：积分可按 1 积分≈5 元兑换（V8.0 §5）；核心业务重要数据/巨大影响问题有每季度评定的 1-50 万特殊现金奖励；每月 3 份最优报告各 500 元打赏；另有个人/团队月度、季度、年度奖。具体金额、活动与兑换规则以平台当前公告为准，本文件不构成金额承诺；京东集团及所属公司员工不得参与漏洞奖励计划（V8.0 原则 19）。
