# 用户提供的 SRC 规则样例对照

本文件整合用户在 2026-09-14 提供的材料，供规则建模与回归使用。各组均未提供可核验的官方 URL、发布/生效日期或完整版本，默认状态为 sample_only；不是当前适用政策。用户/项目明确选定有效规则后，才把相应条款纳入本次运行配置。

## 样例 A：材料中标注字节跳动中国区的规则

| 等级/处置 | 材料中可辨认的主要条件 |
|---|---|
| 严重 | 核心场景/模块系统权限、root/集群权限、服务级关键凭据；百万条以上且可遍历的重要敏感数据；任意账号登录/改密、核心业务重大越权、严重资金/资源逻辑；设备安全机制绕过。金额阈值所在段落有断行，启用前核对原条款。 |
| 高危 | 一般系统权限；5000 条及以上且可遍历的重要敏感数据、租户任意用户信息；自动传播存储 XSS；内网回显 SSRF；重要系统敏感操作和大量核心资源滥用；移动端系统机制绕过/有敏感后果的本地能力。 |
| 中危 | 含敏感信息的完整源码；可归因的内网差异响应 SSRF；部分受限环境/非核心数据 SQLi、有限文件能力；有相应服务器权限的隔离测试系统；存储 XSS、敏感 JSONP；有限高级服务或非核心权益滥用。具体条件不能仅凭名称定级。 |
| 低危 | 已证明请求但无可观察应用差异的 Blind SSRF；敏感 CORS、轻微信息泄露、有限业务越权/权益影响、特定低影响或难利用条件等。频控/反射 XSS/跳转虽被列举，仍受忽略条款约束。 |
| 忽略/暂不收 | 非相关地区/业务或第三方维护资产、外部客户资产；内部已知/优先提交/专项治理；无法复核、无成功案例、无实际危害的扫描或猜测；Self-XSS、无害 CSRF、无意义信息、用户名遍历/SPF、简单 DNS 日志型 SSRF；网络 DoS/不能影响他人的本地 DoS；符合预期或无意义越权，以及列明业务例外。 |

SSRF 要单独区分：仅 DNS 日志、已证明服务端请求但应用无差异、可判断内网服务差异、实际回显。这组材料同时写了 Blind 低危和简单 DNS 日志忽略，不能合并为同一种证据。电商无回显 SSRF 是否收录还涉及实际触发服务的 PSM 归属和审核决定，无法核对归属时为 rule_review，不猜测分类。

材料还明确要求：回显 SSRF 证明到指定程度即可，禁止深入内网；可能导致中断的应用层问题停止测试并作为情报。不能从其高危/严重示例反推允许内网横向、批量数据、Webshell 或实际 DoS。

## 样例 B：未注明平台的 S0–S3 规则

| 等级/处置 | 材料中可辨认的主要条件 |
|---|---|
| S0 | 系统/核心客户端权限，核心数据库或海量核心数据泄露，核心业务 DoS，以及影响所有用户的严重账号/支付流程问题。 |
| S1 | 大量敏感信息的越权/未授权访问，远程任意用户客户端权限或核心 cookie 影响，完全回显内网 SSRF，大量非核心数据泄露与其他大范围用户/资金影响。 |
| S2 | 有实际敏感操作的交互型 CSRF、普通信息泄露/越权/逻辑问题、较小经济影响、部分回显或其他已描述的 SSRF 能力。非 HTTP 协议例举不授予协议/目的地测试许可。 |
| S3 | 轻微信息泄露、限定条件的客户端问题、难利用风险、反射 XSS/跳转/配置问题，以及材料明确列出的无回显 DNSlog SSRF。 |
| 忽略 | 安全无关 Bug、Self-XSS/无敏感操作 CSRF/无敏感 JSON 劫持、无意义信息、无验证的猜测或扫描结果、对正常用户无明显影响的问题。 |

此组没有平台名，不能因 S0–S3 记法就归给某企业。DNSlog 低危与样例 A 的忽略条款不能跨平台混用；需要先确认当前项目采用哪组有效规则及具体证据条件。

## 样例 C：材料中标注快手的规则

| 等级/处置 | 材料中可辨认的主要条件 |
|---|---|
| 严重 | 核心系统权限、核心数据库/海量账密订单数据、核心业务逻辑导致大量利益获取和用户损失；核心系统示例有 passport/支付。 |
| 高危 | 一般服务器/客户端权限；重要业务源码与敏感数据/管理后台；可直接获取大量内网敏感信息的 SSRF；可利用本地代码执行；无需交互的核心业务问题。 |
| 中危 | 一次交互造成用户影响的 XSS/JSON 劫持/CSRF；普通信息、普通路径能力；非核心逻辑与部分存储 XSS；材料中也列出远程 DoS，但执行许可仍独立判断。 |
| 低危 | 特殊条件的信息/XSS、边缘信息、难利用问题、一般 URL 跳转等。需结合更具体的忽略项，不能看到低危示例就承诺接收。 |
| 忽略/暂不收 | 无安全或实际影响、Self-XSS、无证据猜测、部分短信/邮箱轰炸和 PDF XSS、符合预期或不足以满足业务损失条件的问题；已知且正在修复的组件 N-day 在列明修复窗口内；纯内容安全/模型提示响应问题；列明的本地 DoS；未形成实质危害的单接口/参数/功能/账号爆破。 |

N-day 条款要同时核对“平台已知”“正在修复”“窗口起算/期限”和特殊例外；原文的六个月不能变成所有平台通用免收期，外部公开 CVE 也不自动证明平台内部已知。低危本地 DoS 例举与后续具体排除应一起读取；无法确定适用条件时交平台核对，不擅自选择有利条款。

## 三组规则的共同决策与差异

- 共同方向：可利用性、企业/用户的受保护利益、资产价值、规模和成本决定优先级。理论猜测、无影响现象和不符合归属/业务条件的报告不能混入可提交漏洞。
- 不是只收高危：样例明确有中低危及有限风险条款；“实际影响”不能被改写为“必须真实造成资损”，也不能把所有源码/路径/反射 XSS 一概忽略。
- 阈值属于条件：重要敏感数据与普通信息、核心与非核心系统、全量与少量、交互与无交互、可遍历与仅已知 ID 访问，均需证据。不能只匹配 SQLi/XSS/SSRF 名称。
- 更具体的忽略项、地区/业务限制与有效例外优先核对；同一适用范围内仍有矛盾或 OCR 缺字时保留 rule_review。只有等级待定而低阶影响已经可收录时，可以给保守候选结论，不能夸大等级。
- 外部 HackerOne/bug bounty 项目使用其自身有效规则，本文件不强制它们采用这些 SRC 门槛。如何推进与停止统一见 [企业影响与收录评估](../impact-and-acceptance.md)。
