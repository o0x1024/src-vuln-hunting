## 被认可的合规问题类型

1. **征得同意前收集个人信息 / 同意前打开权限**（本族最高产，24 条完成）
   - 判定依据：《App违法违规收集使用个人信息行为认定方法》三.1"征得用户同意前就开始收集个人信息或打开可收集个人信息的权限"；个人信息属性用 GB/T 35273-2020 表 A.1（软件列表、android_id 属个人信息）垫底。
   - 取证：停在前置隐私弹窗**不点同意**，hook 出敏感 API 的完整堆栈+入参+返回值；反复重启复现，证明确非偶发。
   - 案例：8466 / 8468 / 8472（iOS IDFA、IDFV，高危）·9105（AndroidID，高危）·8972 / 8985 / 10496 / 8312 / 8413 / 8419 / 10213。

2. **超出授权范围 / 过度索权 / 违反必要原则**
   - 判定依据：《认定方法》二.3；《网络安全标准实践指南—移动互联网应用程序（App）个人信息保护常见问题及处置指南》2.3.1 过度索权（情形三）。
   - 取证：进主页未触发任何相关功能即弹权限；或**拒绝权限后业务仍被拒绝提供**（把"拒绝即不给用"拍到截图）。
   - 案例：9007 / 9008 / 8995 / 9014（高危"拒绝存储权限则无法拍照上传"）·9000 / 9002 / 9004（中危）·8993（未使用录音/相机即提前申请）。

3. **申请可收集个人信息的权限时未同步告知目的**
   - 判定依据：《认定方法》二.3"未同步告知用户其目的，或者目的不明确、难以理解"。
   - 取证：权限弹窗文案与实际权限不一致（如只写"申请相机权限"却同时要存储）；或弹窗不含目的说明。
   - 案例：8994 / 8997 / 9001 / 9019 / 9050 / 9133 / 9134 ·8382 / 8415 / 8425（"未向用户明示全部的隐私权限"）。

4. **无隐私政策 / 隐私政策无法查看、难以访问**
   - 判定依据：《认定方法》一"未公开收集使用规则"；小程序形态用工信部 164 号文（明示含小程序）把小程序拉进同一标准。
   - 取证：应用内"账号与安全-授权管理/隐私政策"逐级点进去，拍到空页、仅提示"复制到浏览器"、或文字过小过密不可读。
   - 案例：9031 / 9034 / 9047 / 9064 / 9093 / 9094 / 9101 / 9155 / 9158 / 9165 / 8452 / 8474 ·8574 / 8576（原文即写"违反工信部小程序隐私稽核要求"）·9030（难以访问）·9138（文字过小过密）。

5. **第三方 SDK / 共享未逐一列明**
   - 判定依据：《认定方法》二.1"未逐一列出 App（包括委托的第三方或嵌入的第三方代码、插件）收集使用个人信息的目的、方式、范围"。
   - 取证：**双证**——hook 堆栈证明该 SDK 真的在取数（类名+函数+返回值），再截图隐私政策/第三方共享清单里查无此项；仅反编译 Manifest 列出 SDK 不够。
   - 案例：8440 / 8442 / 8800 / 8803 / 8804 ·10648（抖音 SDK 取 AndroidID、MAC、安装列表）·10679（支付宝 SDK 一次取 3 次 AndroidID，兼超频次）·9870 / 9756（反编译 Manifest 取材，作辅助）。

6. **撤回同意 / 注销 / 删除更正 / 副本 / 响应时限 / 反馈渠道**
   - 判定依据：《认定方法》四、五、六各类"未提供…方法/功能"。
   - 取证：走完整产品路径证明该入口不存在或条件不合理，附政策原文对照。
   - 案例：10000 / 10002（撤回）·8434 / 8612（注销）·9048 / 9049（删除更正）·8383 / 8416（副本）·8418（响应时限）·10473（反馈渠道/联系方式）。

7. **定向推送/个性化推荐未提供关闭选项**
   - 判定依据：政策自述存在精准推送却无关闭路径（以"违反自承诺"立论，比纯法条更硬）。
   - 取证/案例：在通知/推送设置里找关闭入口并截图其缺失；10001 / 10009 / 8649 ·10015 / 10019（"以非明示方法征求用户同意"，即默认勾选）。

8. **频繁收集 / 后台静默收集**
   - 判定依据：191 号文"收集个人信息的频度等超出业务功能实际需要"；同一行为短时间内多次调用即为证据。
   - 取证/案例：同一次会话内统计调用次数并记录间隔；8304 / 8313（频繁收集）·8420（后台静默获取 IP）·10317（进入 App 后收集本机 IP 次数超最少频率）·10679（3 次即超频）。

9. **剪切板读写在政策中无说明，或拒绝后仍读取**
   - 判定依据：《实践指南》2.5 情形四"未征得用户同意读取剪切板或公共存储区的个人信息"。
   - 取证/案例：先在系统"应用行为记录"看读取次数，再以取消权限后重复触发作对照；9172（中危，小程序非法获取剪切板）·10012（政策未说明读取剪切板）·9190（拒绝剪切板权限后仍后台静默读取，高危）。

10. **应用分发平台信息明示不到位 / 端间政策不一致**
    - 判定依据：《实践指南》2.7 情形三"隐私政策所述存在明显偏差、错误"。
    - 取证：应用市场详情页 vs App 内政策 vs 官网下载页，逐字对比截图。
    - 案例：8438 / 8447 / 8478 ·9136（App 内与官网页政策不一致）·9149（PC 客户端挂的却是另一产品政策）。

11. **强制捆绑授权 / 频繁索权**
    - 判定依据：《实践指南》2.4.1；《移动互联网应用程序（APP）系统权限申请使用指南》3.1（不得要求一次性授权多个权限）。
    - 取证/案例：拍到"两个权限一次勾选、取消即双拒"与"拒绝后每次进入重复索要"两个对照；9187（登录即索麦克风+相机，拒绝后每次进入重复索要，高危）·9145（一次性勾选相机+存储，取消即两个都不给，高危）。

## 不被认可的典型写法

**声明：语料无"忽略原因"字段，以下从被忽略样本的形态归纳，属相关性推断，非平台因果结论。**

- **只有截图，没有链路**：9635、9872 通篇是政策文案截图与"规范写法应如何"的对照，没有任何一次实际调用来佐证。
- **只有结论，无法证明实际收集行为**：10739 与 10679 题面几乎同构（QQSDK 收集安装列表），10739 被忽略；9872 / 10827 用反编译 Manifest 指出 SDK 存在（Glide、zxing、UMENG），但没证明它取了什么、何时取。反之 10648 给了类名+函数+返回值即被采纳——**"SDK 存在"与"SDK 在取个人信息"是两回事**。
- **无条款依据**：正文样本中带法规条款的完成率 53%（24/45），忽略组仅 23%（5/22）。10646 / 10647 / 10739 全是"违反隐私稽核要求"式的自造依据。
- **无整改建议**：完成组 51%（23/45）写了修复/整改建议，忽略组 14%（3/22）。语料里被采纳的报告普遍含【整改建议】段落。
- **无编号复现步骤**：完成组 22%（10/45）有明确"步骤 1/2/3"，忽略组 9%（2/22）；忽略样本多为一段话+若干截图。
- **纯政策文本/UI 体验类**：首次运行未弹窗（0/21）、敏感信息未加粗（0/5）零采纳。9111 是反例中的反例——它把 164 号文、四部委公告、海南网信办通报案例全引上了，仍被忽略，说明**依据再足也不能替代"实际发生了收集行为"**。
- **同批雷同连投**：10646/10647/10739/10828/11201 集中在 2023-03~04，题面与堆栈模板一致，成批落在忽略侧；同期 10648/10649/10679/10680/10740 同批次却被采纳。堆栈出现率忽略组反而更高（64% vs 38%），可解读为"堆栈已不稀缺，稀缺的是问题选择与条款对位"。
- **笼统打包**："违规收集个人信息""违反多条认定方法"这类标题完成率仅 21%（3/11），不如拆成单点。

## 取证方法

**环境基线（每条报告都要写清）**：App 名+版本号、应用市场来源、机型、系统版本、测试时间。语料里被采纳的报告几乎都带这一组（完成组 71% vs 忽略组 86%——注意这组不是区分项，是底线）。

**Android 动态观测（语料主力手段）**
- camille：`python camille.py -u bluetooth -f 5 <包名>`、`-nu network,app <包名>`、`-t 5 <包名>`；`-u` 指定监控的行为项（bluetooth/network/app），`-f`/`-t` 为触发与时长参数。用于把"未同意前的敏感调用"自动打出来。
- EdXposed/sandhook + Testin safe_check 模块：日志形如 `<App>-->检索运行应用程序-->result:1, 间隔时间…, 第N次, android.app.ActivityManager_getRunningAppProcesses`，随后打 `java.lang.Throwable` 堆栈。
- frida：`frida -U -f <包名> -l hegui.js`，输出 `{"type":"notice","time":"…","action":"获取版本号","messages":"…","stacks":"…"}` 结构。

**iOS 动态观测**：Cydia 插件 hook 系统敏感 API 堆栈，重点盯 `ASIdentifierManager` 的 `advertisingIdentifier`（IDFA）与 `UIDevice` 的 `identifierForVendor`（IDFV）；抓到的堆栈要能落到自家模块（如 `KSPowerWordUtilities`、`PDF`）而非纯系统帧。

**证据五元组（照抄这个格式最省事）**：调用时间 / 类名（如 `android.provider.Settings$Secure`、`android.app.AlarmManager`、`android.hardware.SensorManager`）/ 函数名（`getStringForUser`、`setImpl`、`getDefaultSensor`）/ 入参 JSON 与返回值 / 完整堆栈。10648 即此模板的范本。返回值里的真实设备号一律 `<redacted>` 后再入报告。

**权限时序与拒绝后行为（最容易被采纳的实证）**
1. 清 App 数据、不授予任何权限 → 2. 启动并同意隐私政策 → 3. 到"我-授权管理"截图证明当前零授权 → 4. 触发目标功能 → 5. 观察是否仍发生收集（8866：禁了读写存储，仍能列出手机存储；9190：取消剪切板权限后仍静默读取）。

**隐私政策四清单比对（本语料最强的"违反自承诺"打法）**
同一产品通常有四份清单可交叉核对：隐私政策、应用权限清单、第三方信息共享清单（SDK 清单）、个人信息收集清单。语料使用的路径形如 `privacy.example.com/policies/{privacy,permissions,sdklists,infolists}/<app>`，App 内入口在"我-设置-个人信息收集清单"。方法：hook 到的每一次收集，去四份清单里逐项查；查得到=有明示，查不到=可立论。再叠加应用市场详情页与官网下载页（9136 即用此法定"政策不一致"）。

**"违反自承诺"优先于"违反法条"**：9480 的立论是产品自己的《应用权限清单》把蓝牙权限标为"用户主动使用时弹窗询问"，实测调用前并未弹窗；9656 逐条列出四份清单"均未涉及收集设备蓝牙适配器信息"。厂商自述与实测的矛盾，比抽象条款更难辩。

**抓包（语料里用得少，但补强有用）**：语料主要靠 hook 拿调用栈，网络侧仅零星用于证明"SDK 提前启动后取网络信息"（9504）。若要补，抓包适合回答"这批数据最终发往哪个域名"，hook 适合回答"是谁在什么时候读的"，两者合起来才是完整链路。

**标题写法**：语料中被采纳的标题几乎都是"产品+版本+平台+违规动作+对象"的直陈式（9030、9014、9007、8995），不写"疑似""建议关注"。同一产品多子类问题拆成多条（词典产品在 8994/9001/9004/9136/9138/9145/9149 各成一条），不打包成"存在多个合规问题"。

## 与常规漏洞的取舍建议

**先过项目门槛，再谈技术。** 隐私合规是否收录是强项目相关变量：现有 skill 已记录 ByteSRC、看云 YSRC、合合、银联、麦当劳（部分）等公开声明隐私合规类不收或不计双倍。本语料所属厂商是**明确接收**的一方，不能把它的完成率外推到别家。所以顺序是：读项目规则 → 确认"隐私合规"在收录清单内 → 才开始做，否则一律不值得投入。

**值得投的信号（按语料完成率与等级）**
- 有 hook 堆栈证明"确实收集了"+ 四清单里查无此项 → 双证齐全，最高性价比。
- 同意前/拒绝后仍在收集 → 完成率 33% 且多次判高危（8466/8468/8472/9105）。
- 拒绝权限即拒绝服务（过度索权）→ 完成率 47%，是子类里最高的实质问题。
- 违反产品自承诺（权限清单写了弹窗却没弹）→ 争辩成本最低。
- 一个产品横向覆盖多端多形态（安卓/iOS/PC/微信小程序/支付宝小程序/QQ/百度小程序），语料显示这是同批产出高完成率的主力方式（8xxx–9xxx 段大量同名多端条目）。

**应当放弃或降级的**
- 首次运行未弹窗、敏感信息未加粗、政策文字排版：0% 完成，属产品体验/文案，不投。
- 只反编译 Manifest 说"用了某 SDK"：不投，除非补到实际取数堆栈。
- 同一问题在第 2、3 次重复提交：语料中同批雷同条目几乎全进忽略侧。
- 单条打包"违反多条认定方法"：拆成单点再投。
- 政策文本 vs 法条的纯文本比对（无实际行为佐证）：即便条款引满也大概率忽略（9111 为证）。

**转投渠道**
- 若目标是自家/雇主产品且有内部合规稽核流程，走内部提单更合适——语料 11201 的自述即为"通过 hook 发现…可导致全国稽核通报，故提单跟踪，推动修复"，这类条目在外部 SRC 侧反而被判忽略。
- 客户侧/供应商侧问题（8449、10473 这类站点与协议文本问题）应投对应主体的渠道，不投本产品。
- 需要"厂商内部已知/正在专项排查"之外的独立价值时才投外部 SRC；重复度高的问题外部渠道收益趋零。

**分级口径**：语料里同一子类可从低危到高危跨度很大（超范围收集：中危 9000/9002 vs 高危 8995/9007/9008）。拉开等级的是"是否默认发生、是否全量用户、是否涉敏感信息、是否拒绝后仍发生"，不是条款数量。写影响时把这四点讲清即可，不必自造评分表。

## 可复用检查清单

1. 项目规则是否明确收录"隐私合规"？不收则不做，直接换方向。
2. 记录的六项基线是否齐全：App 名、版本、应用市场、机型、系统版本、测试时间。
3. 是否清空数据并确认测试前零授权（截图"授权管理"页）。
4. 是否停在隐私弹窗未点同意就完成了观测，且反复重启复现 ≥2 次。
5. 每条发现是否都有"调用时间/类名/函数名/入参返回值/堆栈"五元组，而非只有截图。
6. 返回值中的 AndroidID、MAC、IMEI、IDFV、手机号是否已 `<redacted>`。
7. 是否点了具体条款（认定方法章节号 / 实践指南小节 / GB/T 35273 表号），而非"违反隐私要求"。
8. 是否做过四清单比对（隐私政策/权限清单/第三方共享清单/个人信息收集清单），并确认该行为查无此项。
9. 是否对照了产品自述（如权限清单写"使用时弹窗询问"）与实际行为，形成"违反自承诺"。
10. 是否测试了"拒绝授权后"的行为——这是把中危推到高危的关键一步。
11. 同一行为是否统计了频次（1 次 vs 3 次以上），超频次是否单独立论。
12. 是否覆盖了同产品其他端/其他小程序形态（安卓/iOS/PC/微信/支付宝/QQ/百度）。
13. 是否拆分为单点报告，而不是打包"违反多条"。
14. 是否写了可执行的整改建议（"在对应业务功能执行时动态申请"这类具体动作）。
15. 标题是否为"产品+版本+平台+动作+对象"直陈式，无"疑似/建议"字样。

## 相对现有文档的增量点

对照 `references/by-type/mobile-android.md` 与 `references/by-type/miniapp-security.md`（两者均无个人信息保护/隐私合规条目）：

1. **补上整块空白**：两文档只讲组件导出、WebView 桥、存储、签名、越权接口；本文件补"合规类"这一独立问题族，且明确指出它与"越权"不同——前者突破的是监管规则与产品自承诺，不是权限模型。
2. **"违反自承诺"判定法**：现有文档的判定基准是"攻击者实际能做什么"，本文件给出另一条基准——实测行为 vs 产品自己公示的四份清单（隐私政策/权限清单/SDK 清单/收集清单）。这是现有文档没有的判定轴。
3. **证据形态差异**：mobile-android.md 要求调用链+受控数据证据；隐私合规的正确证据是"调用时间/类名/函数/入参/返回值/堆栈"五元组 + 政策截图，不需要受害者数据。本文件补齐这种"无受害者"的取证范式。
4. **拒绝后行为作为核心实验**：现有文档的对照是"合法身份 vs 攻击身份"，隐私合规的对照是"授权前 vs 授权后"、"同意 vs 拒绝"。这一时序对照在现有文档中完全没有。
5. **工具与参数落地**：camille 的实际命令行（`-u/-f/-t/-nu`）、Testin safe_check 日志格式、frida hook 输出结构、iOS IDFA/IDFV hook 点——现有文档只泛泛提"Frida 可帮助观察"，未给可执行参数。
6. **完成率分层可指导选题**：给出 17 个子类的完成率（75%→0%），现有 hunting-strategy 类文档没有这类"哪类白投"的经验分布。
7. **零采纳子类警告**：首次运行未弹窗 0/21、敏感信息未加粗 0/5，明确劝阻两类最容易被新人选中的"教科书条目"。
8. **项目门槛前置**：现有文档把"隐私合规不收"散落在各项目策略页（ByteSRC/看云/合合/银联/麦当劳）；本文件把它提为第一条决策门，并指出该厂商接收，避免以偏概全。
9. **小程序专项补充**：miniapp-security.md 讲身份与签名，本文件补小程序形态特有的合规面（小程序无隐私政策、政策仅可复制到浏览器、未经同意读存储/相机/剪切板），并给出 164 号文把小程序纳入同一监管口径的依据。
10. **未覆盖/待验证**：语料正文对"抓包看 SDK 上报"极薄弱（仅 9504 一条），本文件的网络侧方法是从 hook 证据反推的补强建议，非语料实证；且语料 95% 为 2022 年，2023 年后（个人信息保护法实施细则、App 收集使用个人信息最小必要评估规范后续版本）的条款对位未在语料中出现，投 2024+ 项目需重新核对条款时效。
