## 真实工作流（从语料可还原的完整链路）

语料里可还原出三条完整链路，均以「安装包 → 页堆/调试器 → 单样本 → 崩溃文本 → 打包」为骨架，差别只在平台工具与报告体例。

**1) 版本确认（先定 base，再定 exe）**
- 写明具体四段版本与安装包名：`办公套件 PC 个人版（9584.12012.2019）`、安装包 `办公套件安装包_11.2.0.9281.exe`（[5100]）；Linux `11.1.0.9126`（[2588]）；Mac `2.0.1(3256)`（[2609]）。
- 语料中 433 条只写「最新版」，其中完成率 77%，说明含糊版本不被一律忽略；但正文含完整四段版本的 1486 条完成率 66%，标题带版本号的 701 条 61%——版本号的作用是锁定解析器模块，不是加分项本身。
- 归属到 exe：writer.exe(Word) 298 条/43%、sheet.exe(Excel) 756 条/54%、slides.exe(PPT) 251 条/62%、pdf.exe 247 条/79%、ofdviewer.exe 37 条/97%、photo+.exe 9 条/100%。Word 解析器是全族完成率最低的入口。

**2) 样本构造/变异**
- 语料只留结果不留过程：没有一份 fuzz 配置、种子集或变异日志。可还原的仅有结果命名习惯：单个 `poc.<ext>`（84% 的 zip 内有 poc 命名文件）、BugId 命名 `0000_crash.xls`（[5100]、[5006]）、`poc.ppt / poc.xls / poc.doc / poc.pdf / poc.bmp`（[2388]、[2412]、[2598]、[2781]、[2511]）。
- 跨格式复用是常态而非例外：[2388] 的步骤写「使用 slides.exe 打开 poc.doc」而 WinDbg 参数是 `poc.ppt`；[5112]/[5113]/[5117] 写「使用 sheet.exe 打开 poc.ppt」而参数为 `poc.xls`；[5009] 写「开启 doc.exe 的 PageHeap（gflags /p /enable sheet.exe /full）」。这些是模板残留，说明"构造"环节在语料中不可追踪，只能看到最终触发文件。
- 语料提到样本不稳定但不影响受理：14 条自述「不稳定/可尝试多次打开」（[11918] 原文「可以尝试多次打开，由于堆溢出漏洞，不稳定」），14 条全部完成。

**3) 定位（三套实际命令）**
- Windows：[2388] `gflags /p /enable slides.exe /full` → 打开 `poc.ppt` → WinDbg 以 `poc.ppt` 为参数启动 slides.exe，读 `CommandLine:`、`Access violation - code c0000005 (first chance)` 与 `eax/ebx/ecx/edx/esi/edi/eip/esp/ebp` 寄存器行；[2412] 同法对 `sheet.exe`；[2781] 对 `pdf.exe` 用 `gflags.exe /p /enable pdf.exe /full`；[5306] 用 `gflags.exe -I pdf.exe +hpa +ust`，并在正文注明「开启 gflags 页堆（类似 ASAN，检查程序的越界读等情况）」。
- Linux：[2588] `gdb /opt/vendor/office-suite/appdir/writer` → 打开 `poc.doc` → `Stopped reason: SIGSEGV`、`0x00007fffe7cf7eff in ?? () from /opt/vendor/office-suite/appdir/libio.so`，再 `x/10i $rip` 反汇编；[2579] 用「运行 et → `ps -ef` 查 pid → gdb 附加」，崩溃落在 `__memmove_avx_unaligned_erms` 并给出 `info reg`；[2589] 用 `catch syscall execve` 建立 catchpoint 后再 `run /home/rwx/poc.xls`。
- macOS：[2609] `lldb /Applications/officeapp.app/Contents/MacOS/writer` → 打开 `poc.ppt`；[2618] 同法对 `poc.xls`。Mac 链路只留 lldb 一行，无符号与地址细节，但 Mac项目 78 条全部完成。

**4) 归因（从"崩了"到"哪个模块哪条指令"）**
- 模块级：`ModLoad` 列表 + `eip`（[5107] 的 `pptreader.dll`、[2781] 的 `docpermission.DLL`、[5009] 的 `MSVCR100.dll`）；正文提到 `excelrw.dll` 的 80 条完成率 89%，`office!` 符号形式 317 条 67%，`pptreader.dll` 13 条 85%，`libio/libcore*.so` 25 条约 80%。
- 指令/堆块级（最有说服力的一档）：[5100] 给出 `office!KWebExtension::GetDataSource+0x4ebd` 与 `mov byte ptr [eax+edx],cl  ds:0023:4c601000=??`，随后 `!heap -p -a edx`、`dc edx` 证明目标地址是未分配区。
- 逆向级：[5171] 直接给 IDA 片段与成因 `sub_EEC60(基地址偏移置0)` 调 memcpy 时源串长度小于拷贝长度，摘录 `.text:000EECC5 push esi ; size_t // 拷贝长度`。
- 受控性论证会显著改变结果：正文出现 `exploit/利用` 论述的 91 条完成率 93%；[2599] 写「通过控制 rdi 进而控制…」，[2611] 写「成功劫持 RIP」。

**5) POC 打包**
- 2020 国际线标准包（[5100]、[5006] 同款）：zip 内 `report/` + `0000_crash.xls` + BugId 生成的 `AVW.Unallocated 239.4f9 @ sheet.exe!core.dll+0xB79755.html`；正文首行写「poc 和用 BugId 生成的漏洞详细报告见附件」「附件解压密码为：<redacted>」。
- 2020 国内线：`11.1.0.9584_appError{ea080c0c-b8f0-433d-9da1-345e2b74285a}.zip`（办公套件 自带崩溃包）+ `note.txt` + `poc.doc` + `poc.zip`（[5009]）。
- 2022 后：[10198] 为 `poc.rtf`(51MB)+`poc.mp4`+`poc.PNG`；2026 年 zip 内 mp4 占 43%，录屏取代崩溃文本成为主证据——这是完成率下降段（2022 44%、2026 7%）与证据形态变化在时间上重合的现象，语料未给出因果，只可作观察。

## 各类崩溃的可提交门槛（怎么证明不是"仅崩溃"）

语料没有审核意见字段，因此下列门槛是从「已完成 vs 已忽略」在同类文本上的分布反推的操作口径，属推断而非平台规则原文。

| 类 | 语料中"够了"的形态 | 语料中"不够"的形态 | 可复算信号 |
|---|---|---|---|
| UAF | 释放点+复用点两侧可指认，或 PageHeap 下 `!heap -p -a` 显示已释放块 | 只贴一张 Access violation 与寄存器 | 有崩溃文本的 UAF 46 条完成 85%；无崩溃文本的 981 条完成 48% |
| OOB | 越界地址与所属堆块/数组边界同屏（[5171] 的「at the end of a 96/0x60 bytes heap block」） | 只写"数组越界读取"无边界证据 | 含崩溃文本 327 条完成 64%，不含 245 条完成 81%（反向，见下注） |
| 溢出 | 溢出落点（栈/堆头/DL）+ 可写目标说明（[5024] core.dll 栈溢出、[2610] 溢出堆头） | 仅"程序崩溃" | 全类 70.1%，低于 OOB |
| DoS | 第二机会 C++ 异常 `code e06d7363 (!!! second chance !!!)`（[5009]）、`operator new` 分配失败（[2590]/[2592] 标题即写明）、或 gdb/Linux 下固定指令处的 SIGSEGV（[2588]/[2589] 式取证） | 只说"打不开/卡死" | 含崩溃文本 160 条完成 70%，不含 431 条完成 60%；全族含 SIGSEGV 43 条完成 74% |

注：OOB 出现「有崩溃文本反而更低」的反向分布，与 UAF/DoS 相反。可核对的解释是文本形态差异——高完成率的 OOB 多为 2020 年编号批次的「任意地址读 + gdb 寄存器」干净叙述（标题含「任意地址读」51 条完成 82%），而带大段 WinDbg 原文的 OOB 混入了批量重复投稿。语料不足以判定这是审核偏好，仅记录该分布。

**报告要素（语料中出现且与高完成率同现）**
- PageHeap/gflags 开启命令必须写全：`gflags /p /enable sheet.exe /full`、`gflags.exe -I pdf.exe +hpa +ust`、`PageHeap.cmd sheet.exe ON`（[5100] 附 BugId 仓库脚本链接）。全族仅 28.5% 写到这一层，但写到的完成率 70% vs 53%。
- 崩溃四件套：`CommandLine:`（含 exe 全路径与样本路径）、异常码与机会次（`c0000005 (first chance)` / `e06d7363 (!!! second chance !!!)`）、寄存器行、出问题的模块或符号。
- `ModLoad` 只用来说明加载了哪个解析器 DLL；`kb` 类堆栈在语料中出现 475 次（67%），不是必需项。
- BugId 报告：正文只需抄 `Location / Description / Version / Security impact` 四段（[5100]、[5171]），附件放完整 html。含 BugId 的 117 条完成 107 条（91%），是全族最强信号。
- ASan：语料仅 6 条提及、且是拿 gflags 类比（[5306] 原文「类似 ASAN」）。**语料不含真实 ASan 取证样本，本文不提供 ASan 流程**；WER 仅 13 条，同样不足以提炼规程。

**为何 DoS 63% 而 UAF 仅 50%（语料内可检验的三条）**
1. 分母被批量投稿拉开：UAF 1027 条里只有 46 条带崩溃文本，981 条（95.5%）无任何崩溃证据，这部分完成率 48%；带证据的 46 条完成率 85%。UAF 的 50% 主要是"缺证据的投稿量"造成，不是该类被系统性拒绝。
2. 证明成本与定级不同：DoS 中 490/591 判低危、中位 28 分，一份 second-chance 异常即可闭环；UAF 需同时证明"已释放仍被复用"和"指针可影响"，中位 45 分，缺一环即退回。
3. 重复投稿的代价不同：同一批 DoS 被忽略 216 次仍可换样本再报；UAF 单条价值高但同模块同函数重复即被忽略，语料中 UAF 已忽略 514 次（占全族已忽略的 43.7%）。

## 版本与影响面声明

- 三平台三条命令链，不可混写：Windows 用 gflags+WinDbg（x86 崩溃给 `eip=`，x64 给 `rip=`；语料 x86 标记 337 条、x64 168 条，2020 年模板几乎全是 x86），Linux 用 `gdb /opt/vendor/office-suite/appdir/{writer,sheet,slides}`，macOS 用 `lldb /Applications/officeapp.app/Contents/MacOS/writer`。
- 解析器—扩展名—exe 的对应在语料中稳定：doc→writer.exe、xls→sheet.exe、ppt→slides.exe、pdf→pdf.exe、ofd→ofdviewer.exe、图片→photo+.exe。写报告时把「哪个 exe 打开了哪个后缀」写对，是能否复核的最低条件；[2388]/[5009]/[5117] 的文档内自相矛盾正是反面样本。
- 版本号在标题中的写法：`办公套件 2019 For Linux 11.1.0.9615`（平台+构建）、`办公套件 校园版（11.3.0.9221）`（分支+四段）、`办公套件 PC 个人版（9584.12012.2019）`（分支+build 串）。带版本标题 61%，与全族 57.8% 接近，作用是排除"已修复版本"争议、锁定解析器二进制。
- 影响面声明要素：OS 与位数（[5100]「win10 1909 x86 英文版」）、安装包文件名、进程名、样本后缀。CVSS 向量在 573 条中出现，多为 `AV:L/AC:L/PR:N/UI:R`——本地打开文件类漏洞的标准向量；2024 年 [11918] 出现 `AV:N/8.8` 体例变化，属新模板，不要反推到 2020 年样本。
- 平台完成率差异巨大（Mac 88%、Linux 63%、Windows 58% 按关键词口径），与团队分布强相关，不能读成"某平台更好打"。

## 高频被忽略模式

声明证据边界：归档**不含忽略原因字段**，以下均为标题/正文/团队/附件形态与状态的统计关联，属推断。

1. 同一标题大规模复投而缺单条独立证据：「办公套件校园版存在内存破坏漏洞」27 条、「办公套件校园版Excel程序数组越界访问漏洞」31 条、「办公套件校园版PPT程序数组越界访问漏洞」21 条，三簇全部为已忽略；同期「办公套件国际版存在内存破坏漏洞」43 条、「办公套件 2019国际版excelrw.dll模块越界读取漏洞」41 条几乎全部完成。同标题同类型，差别只在团队/产品线，说明"标题重复"本身不是判据。
2. 正文极短且无崩溃文本：detail<100 字 775 条，其中 426 条已忽略。[12604] 与 [12605] 是同一段 40 字文本（「办公套件的ofd模块存在一处安全问题，利用该漏洞会导致程序崩溃」），一条已忽略、一条已完成——单条无法从文本区分，说明判定还依赖未归档的附加因素。
3. 只有系族名没有函数/模块定位：`office!` 之类符号出现率 67%，无模块偏移的样本完成率显著更低。
4. 样本与 exe/后缀自相矛盾的模板残留（[2388]、[5009]、[5112]）：无法复核"用哪个进程打开哪个文件"。语料未说明这些是否因此被忽略，属风险提示。
5. 把 DoS 写成"内存破坏/UAF"：UAF 中 428 条判低危，多为崩溃即归因 UAF；同一条文若改述为 DoS 反而可能进入受理（低危也收）。
6. 团队字段为空（196 条，完成率 2%）与「校园版」通道（0/116）：作者侧无法控制，但提示投稿通道选择等价于一次预筛。
7. 2026 年样本 136 条完成率 7%：绝大多数处于未审状态，不能作为"当前不受理"的证据。

## 可复用检查清单（样本获取 → 变异 → 归因 → 报告）

1. 先固定四段版本 + 安装包名 + OS/位数，再动手；版本号必须能定位到具体解析器 DLL/so（对齐 [5100] 的 `Version: sheet.exe: 11.2.0.9281 (x86)`）。
2. 确认后缀→exe 对应（doc/ppt/xls/pdf/ofd/图片），并在报告里保持前后一致，避免 [5117] 式矛盾。
3. 样本命名统一 `poc.<ext>`，同批保留原始种子名；BugId 产物用 `0000_crash.<ext>`。
4. Windows 先开页堆再复现：`gflags /p /enable <exe> /full` 或 `PageHeap.cmd <exe> ON`；需要 UST 时 `gflags.exe -I <exe> +hpa +ust`。语料证明写明这一步的样本完成率明显更高。
5. 崩溃文本必须含 `CommandLine:`、异常码与机会次、寄存器行、`模块!符号+offset`；缺符号时保留 `ModLoad` 区间以定位模块。
6. UAF 额外给 `!heap -p -a <addr>`（或 `dc <addr>`）证明块已释放；OOB 额外给堆块大小/边界（「at the end of a N bytes heap block」）。
7. DoS 要落到确定性点（second-chance `e06d7363`、`operator new` 失败、固定指令处 SIGSEGV）；只写"崩溃/卡死"通过率更低。
8. Linux 用 `gdb /opt/vendor/office-suite/appdir/<exe>` 或 `ps -ef` 取 pid 后附加；保留 `Stopped reason: SIGSEGV` 与 `x/10i $rip`。
9. macOS 用 `lldb /Applications/officeapp.app/Contents/MacOS/writer`，样本以参数传入并保留 lldb 输出的模块名。
10. 能做受控性论证就写（EIP/RIP 可控、函数指针可改、地址可写），语料中带此类论述的完成率 93%。
11. 同一模块同一函数只报一次；同族变体合并为一条并说明影响面差异，避免落入 UAF 那 514 条已忽略。
12. 附件固定包成单 zip：`poc.<ext>` + 报告(md/pdf/html) + 截图/必要录屏；沿用批次约定写解压密码。
13. 报告正文按「环境 → 页堆命令 → 打开动作 → 崩溃原文 → 归因（反汇编/IDA/堆块）」五段，目标 >1500 字（语料中该档完成率 71%）。
14. 复现不稳定就明写"需多次打开"，语料中 14 条此类说明全部完成；不要隐瞒不稳定性。
15. 提交前复核：版本—exe—后缀—崩溃模块四者自洽，且样本能由第三方在声明版本上复现。

## 相对现有文档的增量点

对照 `references/by-type/document-rendering.md`（服务端 HTML/Markdown→PDF、导出、后台消费者）与 `references/by-type/desktop-client.md`（localhost/IPC、更新器、Electron/WebView、权限边界），本文补的是**二进制文档解析器的内存破坏取证链路**，现有两篇均未覆盖：

1. 调试器级证据规范：gflags PageHeap 三种写法、WinDbg 崩溃四件套、Linux `gdb`/`ps -ef` 附加与 `catch syscall`、macOS lldb —— 现文档只有"隔离环境无害标记"这一层。
2. 归因层级与受理关联：模块偏移 → 符号+offset → 堆块边界 → IDA 成因，并给出各层级对应的完成率（89%/85%/84%/93%），现有文档没有"证据强度"这一维度。
3. 定量受理基线：子类完成率（DoS 63.2%、UAF 50.0%、OOB 71.2%、溢出 75.4%）、团队与年份差异、BugId 报告 91%、detail 长度与完成率的单调关系。`x-corpus.md` 只有桶计数，没有"这类能过/不能过"的量化口径。
4. 附件与打包规约：单附件 zip、内层扩展名构成、`poc.<ext>`/`0000_crash.<ext>` 命名、解压密码批次约定、mp4 化漂移。现有文档未描述投稿产物形态。
5. 版本声明体例：四段版本/分支名/build 串三种写法与标题写法对复核的作用；`AV:L/AC:L/PR:N/UI:R` 的定级惯例。
6. 明确的能力空白（供后续补采）：语料**不含** fuzz 配置/种子/变异策略、**不含** 忽略原因字段、ASan(6 条)与 WER(13 条)样本量不足、无 triage 去重规则。故本文所有"为什么被忽略"均标注为推断，二进制 fuzz 流程本身仍需另行补证。
