## 被认可的移动端问题

（只列已完成/已修复/已确认；格式：问题类型 → 技术手法 → 影响证明 → 案例 id）

1. **硬编码微信 Secret / 合作方密钥**（信息泄露，中危~高危）→ 反编译取 Manifest `meta-data`、`assets`、`strings.xml` 中的 AppID+Secret（及 AES key、SK）→ 用该 Secret 在微信侧换取 access_token / 会话，证明可代表该 App 接管小程序或第三方能力 → 10469、11022、11041、11278、11339、11358、**11829（高危，多个 SECRET_KEY 可接管小程序）**、5425、6832、6868。
2. **Deeplink/自定义 Scheme 加载任意 URL 进 WebView → 桥 → 凭据外传**（高危~严重，2026 主力）→ scheme/host 不校验，或路由只做 `getCallingActivity()==null` 放行 → 恶意页调 `getInformation()/getSignature()` 取 uid/uuid/token 外传，换设备重放登录成功 → **24303、24398（已修复）**、24320（审核中）、**24663（iOS openWeb，已修复）**、24704（已修复）、24969（`officeapp://` 暴露 69 个端点，审核中）、23899（审核中）。
3. **桥方法粒度过粗（intent 重定向）**（低危）→ 页面可调 `JSIntentSchemeURI`，以宿主身份 `startActivity` → 拉起非导出组件 / 配合 FileProvider 读私有文件；在禁止三方安装的封闭生态里当提权入口 → 23235。
4. **导出 Activity/Service 未授权调用 → 账号接管**（高危）→ 导出组件无调用方校验，直接走登录态逻辑 → 拉起即获得受害者会话写入或资料变更 → 24557（PushTipsWebActivity，已修复）、24366（KFlutterBridgeService，已修复）、11279、11294、11406、11684、11224。
5. **Intent 重定向链**（中危）→ 隐式导出 Activity 校验 `scheme=vendor` 后取 query 参数 `trim` 还原 Intent 再 `startActivity` → 打开受保护组件、向私有目录任意写、可能 RCE → 11222、11223、11226。
6. **WebView JSB 鉴权缺失 / 鉴权条件竞争**（高危）→ 桥注入与域名校验时序错位，或 iOS 侧完全不校验 JSB 调用来源 → 恶意页拿到会话材料 → 账号劫持 → 23931（iOS）、23934（安卓竞争）、12115；24879、24970、24936 同类在审核中。
7. **外部存储日志泄露登录态**（高危）→ `/sdcard/Android/data/<pkg>/files/.../sdk_log/*.log` 明文打印 Cookie/会话，任意 App 可读并正则提取 → 重放为登录态 → 11360；修复后被 11368 以 `MeetingCookieManager.setCookie` 残留打印点绕过复现。同类：11280（日志含全量用户对象）、11094、11310、6548。
8. **任意文件写（Dirty Stream / `_display_name` 穿越）→ 原生 RCE**（中危~严重）→ 恶意 ContentProvider 在 `query()` 的 `_display_name` 注入 `../`，客户端直接拼路径落盘 → 覆盖自带 `.so` 后由正常流程 `System.load`，Toast 回显 `id` 结果 → **24301（已完成，中危）**、24478（严重，已修复）、22898、11231；24228、24675 同类被忽略（同 App 多份报告并存，先查重）。
9. **导出组件 + URI 授权造成私有文件读写删**（中危）→ 导出 `AppLinkActivity` 走 `ACTION_SEND` + `handleLocalFile` 把外部文件落到 sdcard；或 `setPackage`/`IMAGE_CAPTURE` 授出私有 uri 写权限改头像 → 11394、11038（任意文件删除 + 永久登录 DoS）、10523。
10. **三方 SDK 组件暴露**（中危）→ 集成低版本华为 push SDK，其导出组件未做权限约束 → 9515。
11. **iOS 文档解析器崩溃 / 越界读**（低危~中危，批量）→ 构造畸形 doc/xls/ppt/pdf，lldb attach 取崩溃栈，样本 zip 随报告 → iOS DoS 共 27 条（id 集中在 5128–5167 段）、5130 系列 OOB-R、5153（代码执行，高危）；CVSS 统一 `AV:L/AC:L/PR:N/UI:R` 故低危。
12. **本地校验绕过**（中危~高危）→ 应用锁、文档密码、会员功能开关只在前端判断 → 10554、5390、11453。
13. **客户端令牌设计缺陷**（严重）→ 动态令牌可被用于越权（6577 标题即判"致命"，语料未收录正文细节，需自行补证）→ 6577；同类"客户端签名可算"须再证明服务端实际接受，否则只算线索。
14. **从 App 入口发现的服务端越权**（高危，被计入移动端）→ 抓 App 流量改 id → 9683（会议未授权→接管身份）、24539（PDF 转换任务越权读他人文档）；对照：24611（只绕过付费权益）被忽略、24713（fileid 归属缺失）在审核中。

## 移动端逻辑漏洞（为何完成率仅 38%）

- 84 条逻辑漏洞，30 完成、48 忽略。**表面完成率 35.7%（含审核中 42.9%），是全族最低**，但与全族 56.5% 的差距完全来自一处统计假象：
- **48 条忽略里有 30 条是同一根因的逐功能拆条**：23749–23778 全部是「安卓客户端大会员/超级会员专属功能 X 处存在垂直越权，无会员账户可任意使用」，一条一个功能点（图片压缩、抠图、PDF 转 CAD、AI 去水印……），只有首条 **23748 仍在审核中**，后续 30 条全忽略。
- 剔除这批后：53 条中 30 条完成 = **56.6%**，与全族 56.5% 基本一致。**结论：不是移动端逻辑漏洞不被认可，而是"同根因按功能点批量拆条"会被判重。**
- 剩下 18 条忽略集中在四类：支付/签约薅羊毛（7408、7409、12774、12778 并发同订单号多次开通；17255 零余额卡重复下单；11856 注销重注册领新人券；23391 重复建单）、商业规则类（11065 双因素因子依赖、10123 反馈详情越权、9788 小程序模板、23173 游戏刷物品）、权益类（24611 付费 AI 未校验）、会话类但攻击前提弱（24856 消息 URL 污染泄露 `app_sid`）。
- **归属界定（本 SRC 的实际口径）**：
  - 若仅靠普通 HTTP 请求即可复现，且 Web/API 侧同样存在 → 判为服务端资产，从 App 抓包不改变归属；应在提交前用 Web 入口自查是否已存在同根因报告。
  - 只有当"必须借助客户端能力才能触发或扩大影响"时才计客户端成果：导出组件、桥方法、本地存储/日志可读性、客户端签名/加密、本地权限校验绕过。报告里要写清"该增量仅在客户端可达"。
  - 2020 年 9 条 `*.legacy.com` 越权/目录遍历（2189–2194、2198–2200）中 8 条已完成（仅 2192 忽略），说明**早期允许把客户端抓包发现的服务端越权计入移动端**；2024–2026 同类（24611、24856）被忽略，口径已收紧。按当前口径，这类线索应回到服务端资产族评估，不要重复计入移动端。

## 客户端组件与权限（安卓组件权限漏洞 81% 完成率的启示）

- 22 条中 13 完成 + 5 审核中 = **81.8%**；若把已修复计入则 86.4%，仅 3 条忽略。这是移动端**投入产出比最高**的子类。
- 为什么高：每条都能给出"普通三方 App / 一条链接"就能复现的最小链路，影响直接落在账号或私有文件上，不依赖运营规则解释；且同一套静态审计流程可在多 App 间复用。
- 81% 的内部结构值得照抄：
  1. **导出面清点**（`exported=true` 的 Activity/Service/Receiver/Provider + 隐式 intent-filter + `scheme`）；
  2. **入口参数回溯**（`getQueryParameter` → 是否还原 Intent → 是否 `startActivity` → 是否有 `getCallingActivity`/白名单）；
  3. **桥对象清点**（`addJavascriptInterface` 名、`@JavascriptInterface` 方法、是否校验来源域名）；
  4. **落盘/落盘后加载**（`_display_name`、`EXTRA_STREAM`、`handleLocalFile` → 私有目录 → 是否 `System.load`）。
- 高价值升级路径（语料反复出现）：导出组件/桥 → 会话材料泄露 → 账号接管（高危）；文件写 → 覆盖 `.so` → RCE（高危/严重）。单纯"组件可被拉起"多为低危或忽略（2238 的克隆攻击、任务栈劫持 22851 仍审核中）。
- 语料里的反面锚点：`allowBackup=true`（24272）、release 包 `WebContentsDebuggingEnabled(true)`（24633）均被忽略——配置项本身不是漏洞，必须走到"实际读到受保护数据 + 攻击者前提成立"。

## 证据形态

- **Android 已认可案例的常见组合**：真机型号 + Android 版本（11222 用 Android 12/13 双机、24413 用 Android 16 无 root）+ 反编译截图（Manifest/方法体）+ 恶意 APK 源码与 zip + 攻击者服务器接收日志 + 受害者 cookie 换设备重放截图 + 录屏。图片数普遍 10+（11222 12 张、11360 13 张、11394 13 张），说明评审看的是"链"而不是"一句话"。
- **iOS**：lldb attach 崩溃栈 + 影响版本 + 样本 zip（5128 系列）；桥/WebView 类需要受害页 → 桥调用 → 数据外传的完整时序。
- **越权/服务端类**：两个受控账号 + 请求/响应原文 + 受害者视角截图（10123 展示替换 `jobId` 后读到他人反馈）。
- **不要依赖外链**：24413 把复现视频放网盘、24675 只给 zip，二者均被忽略；语料不含忽略原因，无法断言因果，但已认可案例一律把关键证据内嵌进报告。建议证据全部随报告提交。
- 攻击前提必须显式声明并保持真实：普通 App / 一条链接 / 扫码 / 物理接触 ADB。24413 明确声明"无需 root、无需 Frida、无需重签"，仍被忽略——说明前提声明只是必要条件，不构成加分。

## 可复用检查清单

1. 记录包名、版本、`targetSdk`、签名、设备与系统版本、下载渠道；明确当前是否最新版（11368 即因新版修复不完全而复现成功）。
2. 静态清点 `exported=true` 组件与隐式 `intent-filter`，按"能否被零权限 App 拉起"排序，先做 top3。
3. 对每个导出入口追 `getIntent()` 参数：是否 `getQueryParameter()` → 是否 `Intent.parseUri`/`putExtra` 还原 → 是否 `startActivity`；`getCallingActivity()==null` 放行即弱校验（24413/24303）。
4. 清点 `addJavascriptInterface` 名与 `@JavascriptInterface` 方法，标出能取 token/uid、能 `startActivity`、能读写文件的桥方法（`getInformation`、`getSignature`、`JSIntentSchemeURI`、`logincode`）。
5. 检查 WebView 域名白名单与桥注入的**时序**：是否存在 loadUrl 后再校验、或校验后可被重定向绕过的窗口（23934）。
6. 检查 `scheme`/`host`/Universal Link 路由：能否把攻击者 URL 直接塞进内嵌 WebView（24303、24704、24969）。
7. 搜索本地日志与外部存储写入点（`Log.*`、`sdk_log`、`getExternalFilesDir`），用合成标记确认"零权限 App 可读"；修复后复查同名 cookie 打印点（11360→11368）。
8. 追文件落盘：`_display_name`、`EXTRA_STREAM`、`handleLocalFile` 是否拼路径；落盘目录是否在私有路径且后续会被 `System.load`/`dlopen`（24301、24675）。
9. 反编译搜 Secret/key/AES key/SK，按"一个 Secret 一条报告"去重，并用真实换 token 结果证明能力（11829）。
10. 对会员/权益功能，只报**首个可复现的根因**并附完整功能清单，不逐功能拆条（23748 vs 23749–23778）。
11. 支付类先判断是否属于"商业规则/风控"：只有能证明他人订单被充值、金额被篡改、或可规模化资金损失时才值得提交（7644 因订单未绑定用户属此类但仍被忽略）。
12. 从 App 抓到的服务端越权，先回 Web/API 资产族查重并判断归属，再决定是否算移动端成果（2189–2200 的历史口径 vs 24611）。
13. 所有攻击前提写成"攻击者是谁 + 在哪台设备 + 需不需要 root/调试/重签"，并与实际复现环境一致（24413 的零前提声明是标准写法）。
14. 证据内嵌：截图 + 恶意 APK/脚本 + 服务端接收日志 + 换设备重放；不要只给网盘链接。
15. 提交前做同 App 同链查重：24303（完成）/24413、24675（忽略）是同一 App 同一桥链的三份报告。

## 相对现有文档的增量点

1. **给出"deeplink → 任意 URL → 桥 → 凭据外传"四段链的验收模板**，并列出该 SRC 2026 年已收录/已修复的具体桥方法（24303、24398、24663、24704）。现有 `mobile-android.md` 只说明"桥存在不等于可达"，未给可判定的收尾标准（token 换设备重放成功）。
2. **补充"鉴权时序/条件竞争"分支**（23934、23931）：现有两篇文档均未把"桥注入与域名校验的时序错位"列为独立检查项。
3. **补充 Intent 重定向的可判定三要素**（隐式导出 + query 还原 Intent + 内部 startActivity），并给出"`getCallingActivity()==null` 放行"这一常见弱校验写法（11222、24413）。
4. **补充 Dirty Stream / `_display_name` 路径穿越的具体形态与 RCE 收尾**（24301、24228、24675）：现有文档只写"更新、动态加载、文件导入"泛类，没有 `ContentResolver.query` → 拼路径 → 覆盖 `.so` → `System.load` 这条具体链。
