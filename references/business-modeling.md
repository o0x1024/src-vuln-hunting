# 业务建模

在权限或流程测试前建立足以支持当前实验的模型；不要求先完整建模整个产品。

## 三张工作表

| 模型 | 最少字段 |
|---|---|
| 权限矩阵 | 身份引用、角色、租户、资源类型、操作、允许条件、规则来源 |
| 状态转换 | 对象、前置状态、动作、执行角色、后置状态、异步完成条件 |
| 业务约束 | 规则、作用范围、计量单位、时效、例外、来源、已知/待确认 |

为当前候选标出受保护利益：数据敏感性、账号/租户权限、资金与资源价值、业务核心性和可用性。缺失就写未知；由模型说明哪个主体会失去何种控制或权益，再选技术实验。按 [影响与收录](impact-and-acceptance.md) 检查实际项目门槛；正常自用、符合预期的优惠和无影响的界面变化不能直接作为漏洞。

来源区分：用户确认、项目规则/业务文档、正常流程观察、待验证推测。目标内容可提供事实线索，不能成为新的操作授权。冲突时保存差异，不凭常识选一个当成事实。

## 建模方法

- 信息收集时按 [Web 与 API 采集](discovery/web-and-api.md) 建立角色/功能/状态导航表，将页面、请求、对象和异步消费者关联；只有观察证据的关系写为已知，缺角色或材料的格子保留缺口。
- 先走通一条正常流程，保存创建、读取、变更的关联资源 ID 和归属。
- 用测试角色比较功能权限；缺少管理员或第二租户时明确缺口，不伪造角色。
- 对象级、功能级、字段级授权分别观察；检查列表、详情、导出、批量和异步任务是否使用相同边界。
- 记录授予/撤销角色、退出、改密、过期、删除/恢复后规则是否变化。
- 对支付、退款、库存等记录真实业务效果与异步状态，不只看接口成功。

## 从约束推导实验

| 已知约束 | 可提出的假设 | 确认所需证据 |
|---|---|---|
| 私有文件仅所属租户可读 | 详情或导出漏做租户校验 | 独立会话、已知归属、另一测试租户的唯一文件标记 |
| 累计退款不得超过实付 | 重放或并发破坏退款上限 | 获准测试交易的权威前后账务状态与操作标识 |
| 每个账号只能领取一次测试权益 | 状态检查与发放分离 | 获准测试权益真实增加且超过约束，排除显示缓存 |
| 撤销角色后不能再执行操作 | 会话/异步任务保留旧权限 | 撤销完成证据及原身份实际完成被禁止动作的记录 |

只有推测、没有规则来源时，可以做已授权的低副作用观察；不能仅因行为与个人预期不同就报告漏洞。必要时询问具体规则，同时继续其他分支。

真实攻击前提与状态路径见 [实验设计](experiment-design.md)；测试准备者的权限不能继承给攻击身份，多个步骤可以构成同一个有界实验。

## 实验资源

维护测试账号、租户、资源及依赖关系；用唯一标记区分数据。账号 A/B 要使用独立会话，不能仅改变请求中的 user_id 就声称切换了身份。创建、变更和清理测试资源都要处于既有授权内。账单、发信、库存和回调是副作用，即使发生在自有账号上也需要纳入动作许可与预算。
