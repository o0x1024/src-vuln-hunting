# JWT 验签与信任绑定

适用信号：JWS/JWE、访问令牌、ID Token、签名状态

## 检查与最小实验

先确认令牌种类与消费端；普通 JWS 与 JWE 结构不同，可解码不代表伪造。对自有测试令牌分别核对签名、服务端算法允许集、发行者和密钥绑定、audience、时间、用途。

检查 `kid` 选择的密钥是否属于可信发行者，`jku/x5u` 是否只定位可信来源；公钥公开通常是正常设计。改声明后必须看到服务端接受并产生不应允许的测试效果；不能只看客户端页面更新。不同用途的合法令牌互换是独立于签名破坏的假设。

## 证据与反例

无签名或弱算法声明本身不证明绕过，结论依赖协议使用方式与服务端实际信任。过期判断需考虑约定时钟偏差。只签名有效也不足以证明 issuer/audience/用途校验正确。

## Agent 行为

工具保存原始与变体的不可逆指纹、验证端和身份结果；展示内容脱敏。不上传真实令牌到在线解码站，不以泄露密钥或无授权离线爆破补齐条件。

资料核对日期：2026-09-14。来源的证据层级与历史日期见 [来源登记](../research/sources.json)；实验安排是本 skill 的综合设计，不表示已在当前目标复现。

JOSE注册的无签名算法标识是小写none，算法名区分大小写；源帖把None称正确值不符合该注册项。规范也要求无签名JWS按特定对象显式许可，不能默认/全局接受。固定目标实际库/配置/用途，以自有测试令牌核对服务端允许集和真实受保护效果；头字段变化或客户端解码不证明绕过。依据：[RFC7518 §3.6、§7.1.1](https://www.rfc-editor.org/rfc/rfc7518.html#section-3.6)（2026-10-09核对），未向目标发送伪造令牌。

令牌表示变体与撤销键比较时，分别记录原始字符串指纹、传输解码、库验证结果、实际主体/用途及被撤销的会话或签发记录。源帖token+=未给完整语法/实现，不作为通用绕过；[RFC7515 §2](https://www.rfc-editor.org/rfc/rfc7515.html#section-2)的base64url表示省略尾部等号，不能把任意追加字符当合法标准令牌（2026-10-09核对）。只用自有测试令牌，在规则要求撤销后比较原值和有依据的表示差异访问同一合成私密资源，隔离自动刷新、缓存与新签发；可解码或返回200不证明撤销失效。若已有源码，跟验证路径与撤销查询是否针对同一凭据对象，不自行修改验签字符串来“兼容”源帖。

RS256→HS256算法混淆假设需证明验证端把同一可信发行者的非对称公钥材料错误用作HMAC密钥，并允许攻击者选择不应允许的算法；公钥可获得和头改为HS256不够。记录JWK/kid的实际选择、用途、库/允许集、输入密钥类型/表示与最终自有测试身份，TLS站点证书的公钥不自动是JWT签名公钥，不能继承“多半取HTTPS证书”规则。[RFC8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.1)要求核对支持算法及每个密钥的算法绑定（2026-10-09核对）。优先获准源码/配置或隔离样例，线上实验仅用自有测试令牌和明确允许的无害声明；工具生成/客户端解码不能代替服务端接受与受保护能力。

## JWT结构图的编码、验签者与声明名称

三段HS256图只描述一种JWS，不能推广为所有JWT。[RFC7519 §3、§4](https://www.rfc-editor.org/rfc/rfc7519.html#section-3)区分JWS签名/MAC与JWE加密，以及Registered/Public/Private声明名称；图中Restricted不是该分类名称，Private命名也不保证值保密。

[RFC7515 §2及RSA例](https://www.rfc-editor.org/rfc/rfc7515.html#section-2)的紧凑JWS签名输入是编码后header、点号、编码后payload的ASCII字节，通常为无填充base64url，不是原JSON简单拼接或普通Base64；非对称签名可由公钥验证，不能写仅有secret才能验所有JWT。按实际格式/算法/密钥角色核对签名、issuer/audience/时间/业务权限，解码展示和签名有效均非授权成功。不把真实令牌上传解码网站；2026-10-09核读相关段落。

## 令牌换发入口的验签与签发主体

换发/生成JWT的入口也可能先消费旧票据，不因其他业务接口严格验签就获得安全保证。历史图从APK发现generateJwtToken路径，声称去签名/改userid后返回另一个JWT；没有完整请求/响应、算法或实际私密能力，不补成当前已接管。把入口认证、旧票据验签/issuer/audience/用途、主体映射、签发新票据及下游接受串为独立边。

优先获准源码或隔离两个合成身份，核对旧票据声明是否仅在可信验证之后用于选择新签发主体，新票据是否绑定相同稳定身份及正确用途/权限。公开注册票据、合法代签/委派和仅返回不可用字符串为反例；令牌生成不等于取得另一身份能力。保存不可逆指纹及处理器版本，不解包/运行来源APK、重放真人token、生成他人凭据或使用JOSE插件补缺失链。

## JWT格式属性与浏览器凭据运输

旧图称JWT比其他token短、有多种加密算法且可防CSRF，这些都不能从名字推出。[RFC7519 §1/§3](https://www.rfc-editor.org/rfc/rfc7519.html#section-3)将其定义为声明表示，可承载于JWS或JWE（2026-10-09核读相关段）；签名/MAC不是保密加密，实际长度取决声明、头与算法，不能与未指定的其他token作绝对比较。

把格式、验签/用途、保存方式和真实发送条件分开。JWT作为浏览器自动附带的Cookie时仍要沿跨站请求的Cookie/SameSite/Origin及受保护动作核对[CSRF](csrf.md)；手工设置Authorization头的请求又有不同构造条件，不能仅因用了JWT就认防护成立。弱秘密或可选算法题述仍需实际验证端与最终身份证据，不猜密钥、伪造令牌或操作真实账号。

## 邮箱确认票据跨用途与换邮箱后的恢复状态

旧帖把确认链接verifyemail路径改reset-password称成功；另一帖认为改邮箱后旧重置链接还能改密必是bug。签名有效、票据属于某个账号、受众/用途正确与当前流程版本有效分别验证；JWT外观和路由名称不能证明实际票据格式/声明或密码更新。

用隔离自有账号的正常确认/恢复基线，记录签发时稳定ID、地址、用途/期限、换绑规则和消费后权威凭据/身份。按产品承诺区分应撤销的旧票据、合法账号绑定恢复与跨用途错误授权；仅按钮/成功页或测试者拥有全部邮箱不证明他人接管。未生成/替换真实票据、打开来源邮件链接、改账号邮箱/密码或发恢复邮件。

## JWT none 和算法混淆验证服务端允许集合及 key 绑定

JWT 图把解码、签名和资源访问连成流程，并描述 none 与把公钥当 HMAC 密钥的候选。先确认 token 类型和应用用途，再验证服务器允许的算法集合、key 与算法绑定、签名失败对照、issuer/audience 和最终身份。解码成功不等于受信；不签名形式是否可接受取决于已明确的其他保护与应用配置，不能将 none 出现一概判漏洞。[RFC 8725 §3.1–3.3](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.1)要求算法和密钥约束及完整密码操作验证；用自有 token 最小标记，不上传真实 token。
