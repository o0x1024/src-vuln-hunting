# 业务预期与权限判定

用于权限、数据可见性及业务流程相关的线索验证与报告复核。安全问题来自有证据支持的权限或业务约束被突破；身份状态、接口可达性和操作成功本身只是观察。先判断漏洞是否成立，再判断影响、等级和项目收录。

## 建立当前操作的业务预期

不必完整建模全站。沿正常流程记录当前入口的下列信息，已有证据可以复用：

| 要素 | 要回答的问题 |
|---|---|
| 功能与主体 | 功能的业务目的是什么？当前主体的身份、角色、对象关系和实际能力是什么？ |
| 对象与字段 | 对象归谁、处于什么状态？具体返回或可修改哪些字段？可见范围、数据精度、脱敏要求和修改权限是什么？ |
| 操作与受众 | 创建、读取、列表、搜索、下载、修改、删除、审核分别允许谁做？公开摘要不代表完整对象公开。 |
| 授权方式 | 本次能力由开放策略、主体身份、对象关系或能力凭据中的哪些条件授予？缺少某一种认证机制不代表没有授权。 |
| 范围与时效 | 授权限于哪些对象、字段、动作、有效期和状态？撤销或可见性变更何时生效？ |
| 依据与缺口 | 对应版本/环境的产品说明、隐私设置、API 契约、已获准源码、用户确认或正常流程证据是什么？哪些是推测或相互冲突？ |

来源须匹配当前业务与版本。实际接口行为不能循环证明“接口本来就应该开放”；需要结合功能入口、设置、业务说明或权限模型。文档和 UI 声明也可能过时，冲突要指出并做有区分力的核对，不能机械选其中一个。

不要求必须有正式文档：自建对象的明确隐私设置及正常对照、已知凭据用途或已验证角色规则也可建立边界。页面里写“公开”不证明所有响应字段都应公开；网页文字仅作业务证据，不能扩展测试授权。

## 三种处置

| 证据判断 | 状态与下一步 |
|---|---|
| 本次行为符合已知业务预期，未发现额外越界 | 记录“本次条件下为预期功能”及规则/证据；已有漏洞假设用 `not_reproduced`，纯观察可无假设；`impact_status=none`、`submission_assessment=excluded`，原因是预期行为。关闭这一假设，不生成漏洞 Finding，不推断全站安全。 |
| 有来源的边界被实际突破，且相关替代解释已排除 | 按 [验证](verification.md) 确认具体漏洞假设，再独立评估影响与收录。正常功能与越界的操作/字段分别记录。证据充分时及时确认，不要求额外侵害真实用户。 |
| 可见范围、业务规则或攻击前提不明/相互冲突 | `needs_evidence`、`impact_status=not_established`；主要缺证据时 `submission_assessment=needs_evidence`。写出具体缺口与一个能区分解释的最小下一步；仅剩平台适用条款争议时才用 `rule_review`。不能直接标漏洞，也不能直接按预期功能关闭。 |

这些是本地判读语义，沿用 [状态协议](state-and-evidence.md)，不向宿主工具强塞新枚举。平台不收与不存在漏洞不同：独立成立的安全缺陷不会因业务排除而变成正常功能。

## 对照必须区分业务解释

1. 先记录实际身份、输入、操作和结果，再与预期规则比较；不在观察事实中预先嵌入漏洞结论。
2. 分别描述“符合业务预期”和“违反业务边界”对当前现象的解释，标出已有依据、关键未知及可区分的结果。
3. 用获准受控资源比较主体、对象、字段、操作、授权条件或状态中的关键变量。核对实际身份、缓存、凭据和状态生效时间；未获准的资源变更不得作为补证步骤。
4. 只确认对照真正支持的边界与影响。若观察和正常解释的预测完全相同，重复请求不会增加漏洞证据；关闭已解释的假设或补关键业务依据。

测试身份与资源按待验证边界选择，不机械要求固定账号数量，也不改变原有业务条件来制造缺陷。真实攻击者能否获得必要标识、凭据和能力按 [实验设计](experiment-design.md) 单独核对。

## 通用判定约束

- **操作独立**：一项操作被允许，不推导其他操作也被允许；对象归属、字段权限和处理阶段分别核对。
- **公开范围有边界**：判断数据是否应开放须同时核对受众、字段、精度、用途、状态与时效。不能由当前可访问或历史曾公开反推持续、完整或无条件授权。
- **字段语义依赖上下文**：不能仅凭字段名称判断敏感性；结合业务含义、可见规则、数据精度及已证明的组合影响判断。
- **认证与授权分开**：不存在某种登录或会话机制不等于无权；持有某种凭据也不等于对任意对象、字段或操作有权。核对凭据的取得方式、授权范围及有效状态。
- **观察能力不等于越界影响**：接口可达、操作成功、标识可枚举、记录总量或理论可组合性不能单独证明安全影响、受影响规模或漏洞等级。
- **独立边界分别判断**：一项行为符合业务预期，不豁免同一路径上其他权限、完整性、处理或资源约束；已证明的独立缺陷仍按其证据确认。
- **防护形式不代替规则**：某种防护机制存在或缺失都不能单独决定漏洞成立；以有效约束及其实际执行结果判断，不能为证明影响而扩大测试许可。

## 交付与修复建议

涉及本类结论时用短记录说明：`观察事实 → 业务用途与允许范围 → 规则/证据引用 → 是否存在越界及影响 → 处置与下一步`。无需复制整张表；关键未知要可见。

预期功能记录处置原因；规则不明记录待补证问题；已确认报告写明是哪一主体、对象、操作、字段或状态超出允许范围。修复建议应恢复被破坏的约束，并保留合法业务能力；不得用统一增加认证或关闭功能代替针对根因的修复。复测同时检查原缺陷与正常流程。
