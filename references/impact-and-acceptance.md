# 企业影响与收录评估

本 skill 的挖掘目标是找到能证明企业或用户安全利益受损、且符合当前项目收录条件的问题。漏洞名称、可疑配置或技术能力只能帮助定位；优先级与待提交结论由实际影响和适用规则决定。评级、收录和测试许可是独立判断。

## 先建立当前项目的规则配置

从用户/宿主已采用的项目规则提取最少信息：项目与资产归属、适用业务/地区/环境、规则来源与版本/生效时间、收录和忽略条件、等级门槛、平台认可的证明方式、禁止测试动作、已知问题/专项治理例外。允许复用已有有效配置，不为这些字段机械重复询问。

仅有历史文章或多平台摘录时保留为样例，不能自动启用。当前用户提供的三组材料已整理为 [规则样例对照](policies/src-policy-examples.md)。未知条款只阻塞依赖它的等级/收录判断，不阻止现有授权内的正常观察与离线分析。

小米项目可采用已核对来源的 [MiSRC 配置](policies/xiaomi-misrc.md)，贝壳项目可采用已核对来源的 [BKSRC 配置](policies/beike-bksrc.md)，京东项目可采用已核对来源的 [JSRC 配置](policies/jd-jsrc.md)（业务划分、SSRF 收录标准、降级/忽略类型与测试红线），仍须匹配当前项目/版本和产品层。技术专题保持通用；平台的 UGC、Electron、EOL、公开漏洞和附件/人工复核条件不能变成所有项目的排除项。实际权限从输入经过授权到最终消费者核对，不按 AI/App/IoT 标签自动定级。

## 验证与交付时逐步补齐的影响问题

探索阶段按 [分阶段门槛](hunting-strategy.md) 保留未知；下述完整表述是补证方向和交付检查，不是提出候选的前置要求。

用一句话写：具有【起始身份/成本】的人，能够通过【已观察入口】对【不应控制的资源/受保护业务】实施【能力】，影响【数据机密性、完整性、权限、资金、资源或可用性】，证据是【ID】。尚未证实的部分明确标注，不从漏洞名补出整条链。

| 维度 | 应取得的最小有效证据 | 不能代替它的现象 |
|---|---|---|
| 系统/关键权限 | 非预期执行或管理能力，实际执行身份/上下文，资产业务归属 | RCE 标签、版本指纹、只看到一个域名解析 |
| 敏感数据 | 明确的敏感类别与所有者、无权测试身份取得的受控样例、读取能力的限制 | 公开标识、空列表、无意义路径或字段名 |
| 账号/租户 | 被禁止的身份切换、权限提升或对象操作，独立会话和资源归属 | 自己合法访问自己资源、仅更改请求 user_id |
| 资金/资源 | 权威账本/权益/计费状态违反约束，或非预期取得本应付费的受控能力 | 前端金额、两个成功响应、未兑现的假设收益 |
| 可用性 | 已有事故/运行证据，或平台允许的隔离验证及审核认可证明 | 为证明等级主动打断真实服务、普通网络抖动 |
| 低危风险 | 当前规则明确接受的有限能力与相应证据；如限定条件的反射 XSS、有限信息泄露 | 自动把所有低危忽略，或把任何配置建议算作可收录漏洞 |

“实际影响”不要求已经发生真实盗取或资损。两个自建账号可以代表不同授权主体；自建受控数据可以证明跨租户边界。仅影响自身的调试现象与通过自有账号滥用企业付费资源不同，后者仍可能产生企业成本。业务敏感性、核心程度和价值要有依据，不按域名长相猜测。

## 四个独立结论

权限、数据可见性和业务流程相关问题先经过 [业务预期判定](business-intent.md)。证据支持正常功能时，关闭对应漏洞假设并记录预期行为，不能保留为“已确认但低危/不收录”；若业务规则未知则保留待补证，不能用默认排除清单替代调查。

保留现有 hypothesis_status 表示技术假设的证据状态，再增加下述本地评估或宿主等效字段。不要杜撰工具 schema 字段，也不要用它们覆盖平台实际回复。

| 字段 | 值与含义 |
|---|---|
| impact_status | demonstrated：已证明有意义的安全/业务影响；policy_minimum_met：实际证据达到当前规则明确接受的有限能力门槛，尚无更高影响证明；not_established：尚缺影响证据；none：证据支持预期行为或该条件下无有意义影响 |
| submission_assessment | ready：达到可提交证据和当前已知收录条件；needs_evidence：缺关键技术/影响证据或必需提交材料/验证记录；rule_review：规则适用性或平台专属判定待核对；excluded：命中明确不收条件或证实无影响 |
| platform_status | 未提交、待审核、已接收、重复、拒收等，只记录实际回执；未知就保留未知。ready 不等于已接收或保证获奖。 |

奖励资格按需另记 reward_eligibility、reward_basis 与 missing_requirements（本地说明字段，不杜撰工具 schema）。基础/专项/活动分别判断；不满足专项机型、报名或窗口，不自动取消普通项目的已有测试许可和基础报告资格。缺普通提交必需附件/人工验证时保留技术状态并将 submission_assessment 记 needs_evidence；条款是否适用不明时为 rule_review。Agent/第二模型复核不冒充平台要求的人工验证。

ready 需要：目标/动作符合授权、技术事实可复核、impact_status 为 demonstrated 或 policy_minimum_met、当前规则适用且没有已知排除项，普通提交的必需材料/验证记录齐备。policy_minimum_met 必须引用具体条款与满足它的证据，不能凭“某 SRC 以前收过”降低门槛。若平台内部已知库不可见，记录重复状态未知即可，不能凭空保证不重复，也不因此无限等待。

hypothesis_status=confirmed 必须确认一个违反安全/业务规则的漏洞假设；单纯过滤差异、正常计算或预期回调等观察事实放入 proven_facts/实验记录，不能为得到 confirmed 而把原假设改写成已观察现象。只审阅现象且没有漏洞假设时该状态可为空；有假设但反例已否定本次条件时用 not_reproduced，缺关键证据时用 needs_evidence。confirmed 仍不自动等于 ready。技术成立但命中平台业务排除、内部已知或修复窗口时，保留 confirmed 及原始证据，submission_assessment 可为 excluded；不把拒收改写成技术误报。

submission_assessment 表示当前主要处置，理由中同时保留全部已知的证据缺口、规则疑点与动作限制。rule_review 不抹去技术证据不足，needs_evidence 也不表示可以执行未获准的验证。

## 把影响用于选择下一步

1. 先核对当前项目资格、明确排除项和可用条件，再按 [选题与探索](hunting-strategy.md) 比较候选。影响未知但有机制依据、可做区分性实验时可以探索。对核心身份、支付、跨租户、敏感数据等已有具体线索优先补最短证据链；不按名称或奖金强行抬高等级。
2. 技术现象成立但影响未成立时，明确缺的那一环、允许的一个最小对照及结束条件。有机制依据时可验证尚未知的连接；没有依据或不再产生新信息则保留线索，不无界枚举、绕 WAF 或拼接“理论高危”。
3. 当前规则明确忽略且无可信新影响链时停止继续投入；已有线索保留原因。若出现新的具体可收录影响，另立假设，并核对所有节点的动作许可；不能靠改报告标题逃避排除条款。
4. ready 达成后停止为提升等级而扩大获取；需要更高等级证据时先利用已有材料或平台指定无害验证方式。已有可收录结论应及时形成独立报告，不强行追到 RCE/账号接管；具体新影响可另立获准分支，不能因此拖延成熟交付。

来源未知的技术现象、扫描命中、Self-XSS、无敏感操作的 CSRF、公开数据 CORS、正常回调、WAF 放行通常停留在线索或无影响结论；如果当前项目对有限能力有明确收录条款，按该条款评估。不能用这份例表覆盖具体项目的有效例外。

## 默认不收录：通用排除清单（无实际企业/用户影响）

技术成立 ≠ 可提交。以下类别的有限现象默认不进入待提交清单；仅证明现象时记录为 proven_facts/线索。若已独立证明违反安全/业务规则，技术状态仍按证据保留 confirmed，收录状态另记 excluded 或其他实际处置；不得为凑数量（如“至少 N 个高危”）把现象改写为漏洞或标 ready。仅当 (a) 补出真实影响链（见“验证与交付时逐步补齐的影响问题”），或 (b) 当前项目规则明确收录且证据达到 policy_minimum_met 时，才允许进入待提交清单。该清单是通用基线，具体项目有明确收录条款时按项目条款执行。

| # | 默认不收录类别 | 典型表现（包括但不限于） |
|---|---|---|
| 1 | 安全无关的产品 BUG | 产品体验或设计不好、非安全漏洞导致的服务无法访问等 |
| 2 | 无法利用/无实际危害的漏洞 | 不可利用的 Self-XSS（无法分享给其他账号访问、未收到后台记录）、非重要交互（如查询类操作）的 CSRF、静态文件目录遍历、401 认证钓鱼、内网 IP/域名、无敏感信息（按当前规则明确公开或符合要求脱敏的数据）的 JSON Hijacking、横向短信轰炸、CORS 等 |
| 3 | 无任何证据的猜想 | 例如自己或别人的账号被封就说明存在漏洞 |
| 4 | 风险过低或难以利用的问题 | 短信/邮箱轰炸、PDF XSS 等 |
| 5 | 符合业务预期的产品设计或无法造成大量资金损失的问题 | 可自定义充值金额、取消订单领取优惠券等 |
| 6 | 内容安全风险与模型相关问题（非信息安全漏洞导致） | 内容安全风险、与模型提示和响应内容相关的问题 |
| 7 | 非核心业务的本地拒绝服务漏洞 | 其他业务（非核心业务）的本地拒绝服务漏洞 |
| 8 | 移动客户端本地拒绝服务漏洞 | 移动客户端本地拒绝服务漏洞 |
| 9 | 单一目标的暴力破解（未组合形成实质危害） | 仅针对单一接口、参数、功能点或单个账号进行暴力破解（爆破），且未与其他漏洞组合形成实质危害 |

注：本清单保留为本 skill 的默认投入/交付偏好，不宣称所有 SRC 均采用它，也不构成测试授权或普遍技术定性。具体项目明确收录的有效例外优先；涉及“难以利用”“大量资金”等程度判断，不能自行造数值门槛，也不能覆盖已有实际影响证据。

尤其不能把第 6 项用于排除已有跨账号数据/真实工具越权证据的 AI 问题，或把第 8 项用于覆盖特定项目明确区分的持续性设备不可用。平台接受某类影响与本 skill 是否允许实际触发是两个判断；后者仍按执行边界处理。

## 规模、价值与最低证明

- 区分实际验证数、可信资产总量、由共同代码/权限路径推导的可能范围与未验证范围。表中“5000 条”“百万条”是特定样例的等级条件，不是测试任务数量。
- 两个样例或一个 total 字段不证明全部可遍历；规模推断需共同缺陷路径、逐对象限制、资源归属和可信总量等依据。缺少这些证据就标规模未知，按已证实影响保守定级，不能批量读取真实用户来凑门槛。
- RCE 最小执行证明结合资产/权限证据可以说明风险，不要求部署 Webshell；关键凭据泄露结合归属与有效性证据评估，不自行使用生产秘密扩大能力。
- 项目如果提供专用 SSRF 验证服务并明确回显即可，应在该许可和条件内完成归因/回显后停止；不再读真实内网信息来追求“实际危害”。仅 DNS 事件不能替代该回显证明。
- 评级文档列出 DoS、爆破、批量篡改或大额资损，不表示允许执行这些动作。风险验证会影响服务时按项目允许的情报/隔离验证渠道交付；本 skill 的既有执行边界仍然生效。

## Finding 与交付

默认只有 ready 的候选进入“待提交漏洞”与内部 Finding 创建流程；未满足门槛的记录放在实验/假设或补证清单。用户明确要求内部审计归档时，可以记录其他已确认技术问题，但必须标出其影响/收录状态，不能混进待提交成果。

交付分别统计可提交候选、待补证、待核对规则、明确不收/无影响；实际平台接收数量来自回执。只完成技术现象验证而没有可提交漏洞时，应写“本轮无可提交发现”，不能把线索数当成漏洞产出；仍保留实际覆盖与未完成原因。
