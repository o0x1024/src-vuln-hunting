# 专家式建模、实验与经验迁移

在业务深挖、异常难以解释、准备扩展同类问题或复盘时读取。本文把“专家”拆为可训练行为，不按奖金、名气、工具数量或漏洞类型给人分级；下述差异是本 skill 的能力模型，不是白帽群体统计。已有选题、预算、身份、交付与复测规则分别复用 [选题与探索](hunting-strategy.md)、[实验设计](experiment-design.md) 和 [报告](reporting.md)。

## 从第一性原理确定工作对象

系统接收不同主体可控的输入，在状态和信任边界之间转换，并产生数据、权限或业务效果。漏洞证据需要说明：从现实可达到的起点，经实际处理路径，到达一个违反有来源的安全约束的状态。黑盒观察是不完整的，预算也是有限的；因此，下一步应减少会改变决策的不确定性，而不是单纯增加请求或假设数量。

较成熟的工作方式具有以下可观察差异；表中习惯不代表所有初学者，也不意味着每次任务必须完整走一遍。

| 容易受限的习惯 | 可迁移的专家行为 |
|---|---|
| 看到漏洞名便找对应载荷 | 先找攻击者可控量、受保护状态与真正执行检查的位置，按机制选择工具 |
| 用页面/接口列表代表系统 | 跟踪同一对象在客户端、API、任务、消费者和存储中的身份与状态解释 |
| 有差异就继续堆变体 | 保留少量互相竞争的解释，选结果预期不同的低成本实验 |
| 没告警就当阴性、偶发就丢弃 | 核对处理路径和结果判定渠道是否有效，保存偶发结果的条件差异 |
| 成功一次便猜整个产品受影响 | 缩减必要触发条件，找共同根因，再验证有依据的同类入口 |
| 复盘只保存成功PoC | 保存曾经预测、反例、适用前提与失效条件，让下一次少走同样的弯路 |

## 先建立能预测结果的小模型

围绕当前功能短记：**主体 → 可控输入 → 解析/归一化 → 权限检查 → 状态读写 → 最终消费者/效果**。每个节点区分观察事实、代码/文档声明和未知；只补会影响当前实验的环节，不把完整架构图作为启动门槛。

找一个最值得怀疑的隐含假设，例如“前台校验已足够”“任务提交时的身份一直有效”“一次请求中的检查和使用不可分”“显示值就是权威值”“两端用同一键解释对象”。把它改写成可验证问题。HTTP 方法、组件名、相同 URL 或业务人员的简称不足以证明这些假设。

模型的精度依赖业务知识和底层语义。卡在身份绑定、序列化、缓存失效、事务或框架处理顺序时，针对该未知读取已获准的相关代码/当前官方说明，或用可信的小型本地实验核对解析与状态行为，再回到目标事实验证。用具体预测检验理解，不从组件名称猜默认配置；本地成功也不代替部署可达性。仅在这个知识缺口会改变下一步选择时投入，不为显得专业无限钻研无关实现。

可按实际证据选择观察轴：主体/租户、对象键与归属、检查与使用时间、数据表示、处理组件、状态存储和失效传播。优先观察两方解释需要保持一致的连接；只选能检验当前解释的轴，不做全部轴的笛卡尔积。所有候选仍继承原范围和动作许可。

对业务不变量可比较应保持的关系，而不必先知道精确响应：仅替换客户端声明的租户标识不应授予另一租户读取权；同一语义的合法表示不应改变授权结果；若当前规则明确要求即时撤销，撤销完成后便不应沿用旧权限。先核实等价性和合法例外，不能将表示、角色、缓存、配置差异本身当漏洞。

## 让一次实验能改变决定

异常存在多种合理解释时，保留两三个最相关的解释即可：它们分别预测什么、哪个观察会使其失效。若预期结果相同，实验可能只能确认现象，不能区分原因；优先补能区分原因的观察。已有直接且充分的证据时，不强制编造多个解释或追加请求。

先校验**结果判定渠道**：正常受控操作能否被它看见，测试是否到达目标处理步骤，是否仍是同一身份/对象/时间窗口。告警收集器未接入、截断丢掉关键字段、前置校验拒绝、异步未完成、浏览器或工具改写字节都可能使阴性无效。优先利用已有日志/正常流量或获准普通标记做对照；不能为验证检测器去触发真实危险行为。没有观测能力时说明缺口，不以更多载荷补偿。

一次干净反例只削弱其实际覆盖的前提，不外推所有版本、角色和状态；一次偶发异常也不自动确认或否定。保存当时的身份、动态值、对象、先后顺序、版本、网关/消费者及关联证据，在预算内选择能解释差异的对照；不靠无限重试提高“命中率”。新证据否定原解释时更新模型与下一步，保留原预测，不能悄悄改确认条件。

例：撤销后导出仍返回旧名称。可竞争的解释包括旧页面展示与消费者沿用旧身份；先读取关联任务和已允许的权威内容/权限状态。未到最终消费者时不确认泄露；若新证据证明只有名称缓存、私有内容被正确拒绝，停止这条解释。该例用于说明如何区分原因，不要求每次都执行导出或撤销。

## 从一个实例迁移到一类问题

确认后先用已有证据、代码或隔离重放缩减不必要条件，说明哪些字段、步骤和环境是必要的。删除参数导致签名失效只能证明请求失效；删除观察步骤会让结果不可见，也不能反推该步骤是漏洞触发条件。受控线上缩减仅在已有许可、预算和副作用约束内进行；稳定报告已有足够证据时，不为“最短PoC”重复资源变更或拖延交付。

把实例抽象为“缺陷机制 + 所需能力/状态 + 被破坏约束 + 结果证据”，再查可能共享该机制的入口。类比依据可以是共享处理函数、消费者、对象键或修复路径；相同名称、框架版本、相似响应只支持候选。迁移时列出共同点与一个关键差异，先测最有区分价值且获准的代表入口，阴性/已修入口也保留；不将代表样例的结果复制成全部覆盖。

组合链按连接逐边核对：上一环实际交付了什么数据/能力，下一环需要什么身份、可控输入、网络位置、时序与消费者，两者是否真的相接。XSS、SSRF、IDOR 等名称相加不能自动放大等级；某一环充分成立时可先交付其已证明影响，不为了拼链修改真实用户数据或拖延成熟结果。

复用工具的前提同样要经过验证：准确保留字节、身份和时序，可靠捕获关键结果，且其运行成本低于反复手工处理。必要时在任务输出目录制作最小解析/比较适配，先用脱敏材料或已知正常/异常样本检验；工具产出仍需对照原始证据。无需为一次实验先构建通用平台，工具缺失也不改变授权。

## 将经验压缩为可复用知识

仅在出现值得复用的新机制、错误判断或稳定复现时，向当前项目的既有假设/事件追加短记录：**原预测与证据 → 实际结果/反例 → 哪条假设变化 → 新适用前提 → 复用或重开条件**。记录已知版本、身份、部署/业务差异；失败可能是前提不满足、观测失败、工具问题、规则例外或假设被否定，分别处理。

多篇转述同一报告不是独立证据；公开成功案例没有失败投入的分母，不能据此估计命中率或收益。换了协议、语言或产品名后，应检查机制是否仍成立；相同根因可迁移，历史常量、权限、成功率和载荷不自动迁移。

一次任务的经验默认留在受控任务记录，不能自行修改已安装 skill 或跨项目共享秘密。用户要求沉淀到 skill 时，提炼去目标化的前提/反例并增加有区分力的合成案例。评价看能否选到有效实验、识别失效观察、缩小错误推断和保留真实正例；没有配对评测，不能声称该方法已证明优于旧版或达到专家水平。

## FAQ类别定义与实际越过的边界

旧FAQ将IDOR描述为对象引用暴露，将RCE泛化整应用/服务器控制，将SSRF概括为内部资源读写。类别用于选消费者，不替代判据：对象引用可正常公开，需实际不应有的对象/动作能力；解释器执行须界定进程身份、隔离和权限；服务端取址需界定协议、网络可达性、方法和实际返回/状态变化。

XSS跟输入、输出语境、浏览器执行与读者身份，SQL注入跟外来数据如何改变查询语法与数据库作用域。通过“外来输入→真实消费者→违反契约的能力→正常/拒绝反例”检验类别，避免仅凭名称、200或界面字样计漏洞。FAQ展开内容已审，但搜索UI/导出按钮、热度和标签不证明全部索引或所有定义正确；未请求联系人或运行图中代码。来源：[保存帖](https://x.com/i/status/1401092401247047680)。

## 注入分类必须说明语言、解析器和执行 sink

正文混列 SQL、XML、OS、SSTI，以及 DOM-based SQL/XPath/JSON、SSL Injection 等名称。

从输入进入哪一语法、是否被解释成指令和消费者权限出发分类。DOM 描述数据来源/环境，不自动提供 SQL 执行链；JSON 格式变化、TLS 或 XML 名称也不等于注入。没有具体解析器和 sink 时保留为待证假设，不能制造通用漏洞类。
